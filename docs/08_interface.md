# 8. Interface — web UI, API and the latent sphere

> **In one paragraph.** A local single-page app lets a person add tables (and remove them again), follow their processing, explore the dual graph as three views of one knowledge base — a two-plane graph, a 3D latent sphere and an insight table — under one shared legend whose link entries switch the same layers in the graph and on the sphere, inspect any node and chat with the data in Ukrainian, with every data literal left exactly as the data holds it. After an answer, the parts that produced it are highlighted with the same markers in both views: the seed, the themes passed through, the evidence, the scope-disjoint analogues and the exact edges. The console is static files on one origin: it reads the persisted snapshot through the graph service's HTTP API and asks its questions through the narrator's. The only knowledge it changes is a dataset it deletes, through the graph service.

**Code** `insight_graph_service/server/app.py` (FastAPI), `insight_graph_service/server/views.py`, `sig_web_console/static/` (`index.html`, `app.js`, `style.css`, `vendor/cytoscape.min.js`, `vendor/plotly-gl3d.min.js`), `sig_web_console/nginx.conf`, `scripts/dev.py` · **Tests** `tests/test_ui_smoke.py`, `tests/test_sphere.py` · **Previous** [7. Question answering](07_question_answering.md) · **Next** [9. Operations](09_operations.md)

## 8.1 HTTP API

The console and both APIs share one origin, routed by path:

| Path | Served by |
|---|---|
| `/api/chat/…` | the narrator (`evidence_narrator_service/app.py`): `POST /api/chat/query` and `GET /api/chat/health` ([7.5](07_question_answering.md#75-the-language-model-and-citation-check)) |
| every other `/api/…` | the graph service (`insight_graph_service/server/app.py`) |
| anything else | the console's static files (`sig_web_console/static/`) |

In the stack the console's nginx routes them (`sig_web_console/nginx.conf`: uploads stream through up to 200 MB; the graph service gets 300 s to answer and the chat 450 s, the graph's evidence and then the LLM; Docker's DNS is asked again every 10 s, so a re-created service is found without restarting the console; static files carry `Cache-Control: no-cache`, so a browser revalidates them and picks up a rebuilt console on the next load). On the host, `python scripts/dev.py` composes the three on one port with the same routing (http://127.0.0.1:8765, `WEB_HOST` / `WEB_PORT`). Run alone, the graph service (`python -m insight_graph_service.server`) serves its API only. One `Engine` serves all of the graph service's requests; batches and the Neo4j sync at start run on a single worker thread.

| Method, path | In | Out |
|---|---|---|
| `GET /api/health` | — | `{neo4j {enabled, uri, database}, embedding (the workspace's stored representation; null before the first batch), embedding_device, graph (snapshot stats), workspace, problem (why the workspace is degraded; null otherwise)}`; it runs on the event loop, so it answers while a batch runs |
| `GET /api/batches`, `GET /api/batches/{id}` | — | batch records, newest first (404 for an unknown id) |
| `POST /api/upload` | multipart `file`, form `bins`, `categories` (empty = workspace defaults), `geo` (empty = a plain table; [2.9](02_discovery.md#29-spatial-datasets-the-geo-option)) | 202 + the `UPLOADED` record (`Engine.upload`); processing is queued on the worker thread; 413 above `MAX_UPLOAD_MB` (`file_too_large`; the file is not kept) |
| `POST /api/demo` | — | 202; queues the synthetic dataset as `retail_synthetic.csv`, without options |
| `GET /api/graph?dataset=` | optional dataset filter | Cytoscape elements (`views.cytoscape_elements`): `nodes[{data: id, kind, label, full_label; Pattern: weight, direction, ptype, dataset, support, target, effect, scope[], anchor, anchor_label; Attractor: mass, n_patterns}]`, `edges[{data: id, source, target, type, plane, weight, weak}]`, `stats` |
| `GET /api/nodes/{id}` | — | `{node (all props), neighbors {TYPE / "TYPE (in)": [{id, label, kind, weight, props}]}}` (`views.node_details`; 404 for an unknown id) |
| `GET /api/sphere?dataset=` | optional dataset filter | the projected sphere as data (`views.sphere_points`, [8.4](#84-the-latent-sphere)): `{points [{id, kind, xyz, hover; Pattern: cls, weight; Attractor: n_patterns}], edges [{id, type, source, target, weak}], message}` |
| `GET /api/geo` | — | the READY geo datasets: `[{dataset_id, filename, option, resolution, location, cells, points, sparse_cells, min_cell_points, base, moran_i, sac, metrics}]` (`Engine.geo_datasets`) |
| `GET /api/geo/{dataset}/cells` | — | a GeoJSON `FeatureCollection` of the cells (`id` = cell row; properties `h3`, `row` and every cell-table column, NaN → null), `bbox`, `meta`, and `patterns [{id, rows, scope, target, effect_size, phenomenon_type, support, weight, spatial}]` (`Engine.geo_cells`); 404 `unknown_dataset` for a dataset without `geo.npz` |
| `GET /api/geo/{dataset}/patterns/{pattern}` | — | `{pattern_id, cells, rows, n_points, points}` — the pattern's cells and an even sample of at most `GEO_MAX_POINTS` (5000) of its points as `[lon, lat]` (`Engine.geo_pattern`) |
| `POST /api/search` | `{question}` | the `EvidencePayload` of the question ([7.5](07_question_answering.md#75-the-language-model-and-citation-check)); 400 for an empty question |
| `DELETE /api/datasets/{id}` | — | removes the dataset from the knowledge base ([6.8](06_graph_and_storage.md#68-deleting-a-dataset)): `{dataset_id, batches, patterns_removed, anchors_removed, neo4j}`; 404 for an unknown id, 409 while one of its batches runs |
| `POST /api/reset` | — | deletes the workspace and, with `NEO4J_ENABLED`, clears the mirror: `{status: "reset", neo4j}`; 409 at once, without waiting, while a batch or a deletion runs or an upload waits; also the way out of a degraded start |

**Refusals.** One exception handler turns every refusal of the engine ([9.4](09_operations.md#94-error-codes)) into the body `{detail, code}` with the status of [12.4](12_architecture.md#124-services-and-contracts). An unknown batch or node is a plain 404 `{detail}`.
- **An empty graph is no error.** The read routes return empty elements, and `/api/search` returns the empty payload.
- **A degraded workspace** ([6.5](06_graph_and_storage.md#65-versions-degraded-start-and-reset)) serves the empty state on the read routes and names its reason in `/api/health` (`problem`). Upload, demo, search and deletion answer 409 `workspace_degraded` until `POST /api/reset`.
- **A representation fingerprint** other than the workspace's refuses `/api/search` with 409 `representation_mismatch` and fails a batch at EMBEDDING.
- **A sphere that cannot be drawn** answers 200 with no points and a `message`: no insights yet, or fewer than four points (insights + themes).

## 8.2 The single-page UI

Plain HTML, JavaScript and a design-token stylesheet with light and dark themes; no framework. Cytoscape.js 3.30.2 draws the graph and plotly.js 3.6.0 (its `gl3d` partial bundle) the sphere; both are vendored in `sig_web_console/static/vendor/` (`sig_web_console/PROVENANCE.md`), so the console loads nothing from a CDN and works offline. It reaches both services through relative `/api/` paths on its own origin.

* **Top bar** — health pills: the LLM (reachable / model found, from `GET /api/chat/health`), the Neo4j mirror on or off and the embedding model and device (from `GET /api/health`), refreshed every 30 s and after each READY batch; *Server unreachable* when `/api/health` fails. A theme toggle (remembered in the browser).
* **Datasets rail** (left) — a drop zone for CSV, TSV, TXT and Parquet files; *Column options*: *Treat as categories* (`categories`) and *Split numbers into bands* (`bins`); *Analyse* and *Try demo*. One card per dataset (its READY batch, otherwise its latest attempt). While running: a progress bar and the stage in plain words ("Searching subgroups… step 4 of 10"). When READY: insights, themes first learned from it and rows, then columns, subgroups tested, filtered out, duration and dimension tags. When FAILED: a plain-language title, the cause and a tip per error code (for `no_candidates`: mark number-coded columns as categories). Clicking a READY card focuses all three views on that dataset — the dataset → insights → themes chain is the same filter everywhere. A **Delete** button at the foot of every finished card — READY, FAILED or SKIPPED — asks for confirmation and calls `DELETE /api/datasets/{id}` (the batch id for an upload that failed before it had a dataset id): the backend removes the dataset ([6.8](06_graph_and_storage.md#68-deleting-a-dataset)) and the rail and the views reload from it, so what is shown is always what is stored. The rail polls every 0.9 s while a batch runs (every 3 s after a failed poll) and reloads the views when one becomes READY. While the workspace is degraded ([6.5](06_graph_and_storage.md#65-versions-degraded-start-and-reset)) the rail shows the reason from `GET /api/health` and a *Reset workspace* button, which asks for confirmation and calls `POST /api/reset`.
* **Canvas** (centre) with the view tabs **Graph | 3D Sphere | Insights** — three views of the same analytical state —, the dataset filter, the graph's layout selector (*Two planes* / *Force*), *Fit* (fits the graph, resets the sphere camera), *Legend* (shows or hides the legend column; remembered) and *Clear highlight*. Left of the view sits the **legend column** ([8.3](#83-one-visual-language-for-the-graph-and-the-sphere)), the same for all three views: a caption (`52 insights · 7 themes in view`), the node classes, the link layers as switches and the answer markers, each with its count in the current view (the answer counts appear after a question). Hovering an entry spotlights its elements — the rest dims, in the graph and on the sphere.
* **Columns** — the borders between the datasets rail, the canvas and the chat can be dragged (rail ≥ 220 px, chat ≥ 300 px, the canvas keeps ≥ 380 px); widths are remembered in the browser, and a double-click on a border resets it.
  * *Graph* — the *Two planes* layout puts themes in a top row ("THEMES"), ordered by a greedy chain over theme links (RELATED_TO or CO_OCCURS) so that linked themes sit side by side, with RELATED_TO as arcs labelled by weight and CO_OCCURS as dashed lines; insights sit below ("INSIGHTS"), grouped under their strongest theme; Dimension and Metric nodes form a bottom row when the *Columns* layer is on. A *Force* layout is also available; switching layouts keeps the elements, the layer state and the highlight.
  * *Insights* — a sortable, filterable table (where, metric, effect, rows, evidence, theme); a row opens the details drawer.
  * *3D Sphere* — [8.4](#84-the-latent-sphere), drawn in the page by plotly.js and as interactive as the graph: the legend's switches show and hide its link layers in place (Columns is disabled there: column nodes have no vectors), hovering a legend entry spotlights it, a click on an insight or a theme opens the same details drawer, evidence cards isolate their path; rotate, zoom and hover as usual, *Fit* resets the camera.
* **Map** (a fourth tab, shown once a geo dataset is READY; `sig_web_console/static/geo.js`) — [8.7](#87-the-map).
* **Details drawer** (node click, table row, citation or neighbour) — an insight opens with a one-sentence reading of its target ("discount is higher here — median 19.19 vs 10.74 overall (+2.21 sd)"), the shifts with meters and the evidence facts (rows and share, evidence weight, adjusted p, bootstrap stability, correlation change, confounders, aliases; a correlation-change insight leads with its correlation change, lists its median differences as *not validated*, and shows p as *not tested* and stability as *not measured*), then collapsible *Score breakdown* (weight factors, SD, EMM, volume), *Canonical representation* and *Provenance* (dataset, batch, selector, engine, rows reference, embedding spec). A theme shows its signature and mass, evidence mass and dispersion. Connections are grouped under plain names ("Belongs to theme", "Narrower insights", "Contrasts with", …) and are clickable.
* **Chat** (right) — a welcome card with suggested questions; user and assistant bubbles; a typing indicator while the graph is searched; the answer rendered from light Markdown (headings in either script) with clickable `[P#]` citations (grouped `[P1, P3]` too; the pattern id is in the tooltip) that open the drawer; chips for the model and latency (or "Evidence only"), "n sources cited" (or "No citations" when the check failed) and the cross-segment count; an *Understood: маржа → margin · телефонів → phones* line when words of the question were grounded onto data literals ([7.1.1](07_question_answering.md#711-literal-grounding)); then three panel tabs, all closed until clicked (a click on the open one closes it again): **Evidence & how it was found** — a transversal-check line and one card per item (key, role badge *match* / *lattice* / *via theme*, an *other segment* badge, scope, the top two shifts — for a correlation-change insight its relationship instead —, rows, evidence, path chain) —, *Sources* (the provenance footer) and *Prompt* (the exact evidence the model saw). Follow-up suggestions are derived from the evidence (the first theme, the first cross-segment item, the seed's correlation pair). A notice above evidence-only answers comes from `answer_mode` / `llm.error`, never from the answer text. Enter sends, Shift+Enter breaks a line; *New chat* clears thread and highlight; a switch turns the LLM explanation off. A question goes to `POST /api/chat/query`; the console reads the answer's own fields (`answer`, `answer_mode`, `llm`, `citations`, `prompt`, `provenance_footer`) and the graph service's `view` passed through by the narrator (evidence cards with the parse, traversal baselines, highlight groups).

  **Language.** The application chrome — navigation, tabs, buttons, labels, legend, drawer, table, status texts — is English. The chat's natural language is Ukrainian: the suggested and follow-up questions, the model's answer (system prompt rule 7, [7.5](07_question_answering.md#75-the-language-model-and-citation-check)), the evidence-only summary and the transversal-check note. Every data literal stays exactly as the data holds it, in its own script — column names, values, dataset names, ids, `[P#]` keys: *"Чому margin нижчий для phones у US?"*, never a translated or transliterated `margin`. The parser matches those literals as typed and reads the Ukrainian direction and relationship words by stem ([7.1](07_question_answering.md#71-from-question-to-query)), so a Ukrainian question retrieves exactly what its English twin does.

## 8.3 One visual language for the graph and the sphere

The graph and the sphere are two projections of one snapshot, so one meaning has one label and one marker in both. The legend column is that contract, and its link entries are the layer switches for both views: a switch restyles the sphere's traces in place (`Plotly.restyle`), without a new projection. One key ties the three sides together: a legend entry's `data-key` in `index.html` names its graph selector in `app.js` (`MARKS`, and `LEGEND` with the answer markers; the counts come from the same selectors) and is the `meta` of every sphere trace it explains (`sphereTraces`) — display names join nothing. By default only **Hierarchy** and **Theme links** are on. Colours are the theme tokens of `style.css`; the sphere reads the same tokens at every draw (`spherePalette`), so it follows light and dark mode.

| Legend entry (key) | Meaning | Graph | Sphere (trace `meta` = key) |
|---|---|---|---|
| **Theme** `anchor` | a latent anchor | purple hexagon, size ∝ members, labelled with its two strongest signature entries | purple diamond, size `8 + 1.2 · members`, labelled `A-k` (`Themes`) |
| **Metric higher** `up` | an insight whose primary metric is higher in its subgroup | blue circle, size ∝ evidence weight | blue circle, size `3 + 6w` |
| **Metric lower** `down` | … lower | orange circle | orange circle |
| **Correlation change** `cov` | a covariance insight | green rounded square | green square |
| **Hierarchy** (toggle, on) `lattice` | SPECIALIZES: narrower subgroup of | grey arrow from the narrower insight to the broader one; GENERALIZES (its inverse) hidden | grey line |
| **Contrasts** (toggle, off) `contrast` | CONTRASTS: overlapping scope, opposite shift | red dashed line | red dashed line |
| **Siblings** (toggle, off) `sibling` | SIBLING: same parent, another value | dotted line | dotted line |
| **Theme links** (toggle, on) `latent` | RELATED_TO: mutual nearest centroids; CO_OCCURS: themes sharing member insights | thick purple arc labelled with its weight; dashed purple line | thick purple line; dashed purple line (*Co-occurring themes*) |
| **Memberships** (toggle, off) `activates` | ACTIVATES: insight belongs to theme; dashed = weak (coverage only, not walked) | thin lilac line, width ∝ alignment, dashed when weak | thin lilac line, dashed when weak (`Memberships`, `Memberships (weak)`) |
| **Columns** (toggle, off) `schema` | Dimension and Metric nodes with HAS_SCOPE / TARGETS | grey tags in a bottom row | not drawn (no vectors); the toggle is disabled in the sphere view |
| **Seed** `seed` | an insight matched directly to the question | thick gold ring | gold ring |
| **Evidence** `ev` | an item shown to the model (cited or not) | thin ring in the graph's ink colour | ring in the ink colour |
| **Other segment** `cross` | a cross-segment item: reached only through a theme, no shared condition (`transversal_only`) | double red ring | red ring |
| **Answer path** `path` | the edges of the paths used | thick gold edges | thick gold lines; themes on the path get a gold ring (`Themes visited`) |

After an answer everything else fades (graph: opacity; sphere: insight opacity and faint memberships) and the answer stands out with those markers; a visited node that is not evidence keeps full brightness without a ring. Clicking an evidence card isolates **that** path (seed → theme → insight) and zooms to it; in the sphere view the sphere is redrawn with that path from the projection it already holds. The isolated path is the current highlight (`S.hl`) until another answer or *Clear*: a layer switch, a view switch or a dataset reload redraws it, not the whole answer. A path is drawn even when its link layer is switched off. If the dataset filter hides the evidence, the filter switches to the evidence's dataset first.

## 8.4 The latent sphere

The graph service projects and the console draws. The projection is lac's prosphera projection (`views.project_to_sphere`, the same scikit-learn calls; no projector is vendored and prosphera is not a dependency), fed with insight vectors and anchor centroids instead of text chunks and concepts. On the stacked matrix `[P ; A]` (one frame, one commit):

```text
per-feature robust scaling (median, IQR over the 5–95 % quantile range)  →  KernelPCA(kernel = cosine, 3 components)
→ centre by the mean  →  u = y / ‖y‖,  radius = minmax(log ‖y‖²) ∈ [0.1, 1]
```

Points lie inside the unit ball: the direction comes from the kernel PCA, the radius from the (log) spread. The kernel PCA's random state is `RANDOM_SEED` (42), so one commit always projects the same way. `views.sphere_points(state, seed, dataset)`, behind `GET /api/sphere`, takes the patterns — of one dataset when the filter is set, so the projection is refit on the subset — and the anchors they activate. It returns every placed point with its id, kind, class (`up`, `down`, `cov`) and evidence weight or member count, its coordinates and its hover text, plus every edge whose two ends are placed (the lattice edges, ACTIVATES with its `weak` flag, RELATED_TO and CO_OCCURS). An insight's hover names its primary theme (`views.primary_anchor`, its strongest membership) and the alignment.

The console (`sphereTraces` in `app.js`) draws it in the graph's language ([8.3](#83-one-visual-language-for-the-graph-and-the-sphere)):
- one trace per insight class and per link layer, each tagged with its legend key as `meta` and starting with the visibility of its toggle;
- the themes as labelled diamonds;
- six faint half-axes and three great circles for depth;
- with a highlight, the answer-path lines and the seed, evidence, other-segment and themes-visited rings.

The drawing has no title and no Plotly legend of its own — the legend column explains it — and its colours are the console's theme tokens. Membership proximity, not colour, shows which theme an insight belongs to; hover text names the theme and the alignment.

The console fetches the projection once per graph and dataset filter. An answer, an isolated path or a theme change redraws the traces from it (`Plotly.react`, the camera kept) without a new request; layer switches and the legend spotlight restyle the live traces. Every insight and theme point carries its node id (`customdata`), which is how a click opens the drawer. Three dimensions cannot preserve 1152-dimensional cosines: visual closeness on the sphere is a hint, the stored cosines are the truth ([5.7](05_latent_anchors.md#57-links-between-anchors)).

## 8.5 Text shown to people

| Surface | Code | Format | Example |
|---|---|---|---|
| headline — graph node `label`, Neo4j `label`, evidence `headline` | `insight_contracts/text.py::headline` | ASCII: `<attr>=<value>, …: <target> <±z> sd`; covariance `<scope>: corr(<a>, <b>) strengthens|weakens|reverses` | `category=phones, region=US: discount +2.21 sd` |
| graph node label (`/api/graph`; `full_label` = headline) | `views._short_label` | the condition **values** joined by ` · `, a line break, `<target> <±z> sd` or `corr(<a>, <b>)` | `phones · US` / `discount +2.21 sd` |
| table and drawer | `app.js` | scope tags `attr = value`, metric `human(target)`, effect `±z sd`; drawer lead `<metric> is higher/lower here — median <local> vs <global> overall (<±z> sd)`; covariance: `The relationship between <a> and <b> changes here: correlation <global> overall → <local> in this subgroup.` | |
| anchor label | `snapshot._attractor_nodes` (`insight_graph_service/core/snapshot.py`) | `discount ↑ · margin ↓` | [5.8](05_latent_anchors.md#58-how-an-anchor-is-described) |
| sphere hover, insight | `views._pattern_hover` | `Insight <id>`, `Scope: category=phones ∧ region=US`, `Target: discount (shift)`, up to three shifts `metric: local vs global (z ±x)` (raw column names), `Support: n rows · evidence w`, `Theme: <label> (alignment a)`, `Dataset: <file>` | |
| sphere hover, anchor | `views._attractor_hover` | `Theme A-k`, label, `Insights: n over d scopes`, `Mass: m · evidence mass e`, `Columns: …` | |

The node label shows condition values without their columns, so `q2 · NEAR BAY` does not say whether `q2` is an income or an age band; the drawer and the headline do. UI vocabulary (glossary [11.1](11_reference.md#111-glossary)): attractor → *theme*, pattern → *insight*, `insight_weight` → *evidence*, robust z → `±x sd`, ACTIVATES → *membership*, RELATED_TO → *theme link*, CO_OCCURS → *co-occurring themes*, transversal-only → *other segment*; `human()` replaces underscores in column names. Ids (`P-…`, `A-k`) stay visible in path chains so that the UI, the prompt and the journal agree.

## 8.6 Configuration, failure modes and tests

`WEB_HOST` (127.0.0.1), `WEB_PORT` (8765): where `scripts/dev.py` and `python -m insight_graph_service.server` listen. In the stack the graph service's image sets `0.0.0.0:8000`, and the console's nginx is published on `SIG_WEB_PORT` (8765). At start the graph service checks the model files against the pinned manifest before anything touches the workspace (exit 3 when a file is missing or has the wrong size, naming `python -m insight_graph_service.core.model_store`). It then opens the workspace (exit 2 while another writer holds it), warms up the embedding model and logs the device and free GPU memory.

API errors are shown inline (upload message, an error bubble in the chat with the refusal's `detail`). Failed batches show the plain-language explanation and the raw `error.message`. An offline LLM shows a red pill and evidence-only answers with a notice; an unreachable graph service shows *Server unreachable*. Because the views are derived from the persisted snapshot, a UI failure cannot invalidate stored knowledge.

Tests run the console on the `scripts/dev.py` composite (`dev.compose`): the graph service, the narrator with a fake LLM and the console's static files on one local port.
- `test_upload_process_render_query`: the page and its vendored scripts served; upload, poll to READY; graph elements with the four main node kinds and eight edge types; node details; a Ukrainian question through `/api/chat/query`, parsed to its literals, with the highlight's edges resolving in the graph; deletion through the API emptying batches and graph, 404 afterwards; a failed upload deleted by its batch id; reset.
- `test_browser_renders_graph_and_highlights_path` (`browser` marker; headless Chromium found under the Playwright browser folder of `%LOCALAPPDATA%`). It renders Cytoscape, the READY card and the health pills, and lists every insight in the table. It runs a Ukrainian suggestion and asserts highlighted edges, themes, seeds and evidence cards, the answer's panels closed by default and the evidence opening and closing on click. It opens the drawer from a citation. It checks the legend: visible, only Hierarchy and Theme links on, its counts, the hover spotlight. On the sphere drawn by plotly.js, the Memberships and Hierarchy switches change its traces and the graph edges, Columns is disabled, and a click opens the drawer. An isolated evidence path survives a layer switch. It drags a column border, toggles the theme, deletes the dataset from its card and sees the views empty, with no page errors.
- `tests/test_sphere.py`: every insight and the themes it activates placed inside the unit ball, with classes and hover text, and edges only between placed nodes; an answer's highlighted edges resolving among the sphere's edges; a deterministic projection served by `GET /api/sphere`; the message on an empty workspace.

## 8.7 The map

The **Map** tab draws the H3 cells of a geo dataset ([2.9](02_discovery.md#29-spatial-datasets-the-geo-option)) with MapLibre GL JS 4.7.1 over an **offline** basemap: country borders (Natural Earth 10m, the Ukrainian point of view), first-level boundaries, rivers, lakes, populated places with their Ukrainian names (`sig_web_console/static/vendor/geo/`, `PROVENANCE.md`) and a one-degree graticule. Nothing is fetched from outside the console's origin. The map keeps its dark tactical palette in both themes. It shows the dataset chosen in the dataset filter when that one is a geo dataset, otherwise the first one.

* **HUD** (top left) — the file, resolution, cells and points, and the SAC line `significant without → with the n_eff correction`; *Colour cells by* any numeric cell column (seven quantile classes; NaN cells stay dark); layer switches *Cells*, *Hot / cold spots* (glowing outlines of `lisa_points`), *Events*, *Borders*, *Places*.
* **An answer** paints the cells of every cited insight of a geo dataset — orange where its target is higher, cyan where lower, green for a correlation change; P1 wins a shared cell — dims the rest and fits the view to them. The **tour bar** (top right) lists the keys; a key focuses its insight, *▶ TOUR* flies through them every 4.2 s. A citation `[P#]` or an evidence card clicked while the map is open focuses that insight instead of the graph. A second click on the focused key, the card's ×, or Esc removes the focus; *✕ CLEAR* (or *Clear highlight*, *New chat*) removes the whole answer from the map.
* **Focus** — a pulsing amber outline on the insight's cells, its points (`GET /api/geo/{dataset}/patterns/{pattern}`) as glowing dots, and a card: key, scope, shift, cells, compactness, points, `n_eff`, Moran's I, weight, and the retrieval path.
* **A cell click** opens a popup: the cell id, its LISA class, every non-null cell column, and the insights covering it (most weight first; a click focuses one). *Запитати про цю зону* asks the chat about the cell's strongest insight's scope.
* The cursor line (bottom left) shows coordinates, zoom and the cell under the pointer; the welcome card of an empty chat and the follow-ups after a geo answer offer questions in everyday words, without column names: the hottest zones (when the dataset has hot spots), where a category value occurs more often (the strongest share insight, e.g. «Бомбер»), where events are fewest (when an insight has a quietest-quarter neighbourhood), and zones that look alike in different places.
