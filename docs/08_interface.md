# 8. Interface — web UI, API and the latent sphere

> **In one paragraph.** A local single-page app lets a person add tables (and remove them again), follow their processing, explore the dual graph as three views of one knowledge base — a two-plane graph, a 3D latent sphere and an insight table — under one shared legend whose link entries switch the same layers in the graph and on the sphere, inspect any node and chat with the data in Ukrainian, with every data literal left exactly as the data holds it. After an answer, the parts that produced it are highlighted with the same markers in both views: the seed, the themes passed through, the evidence, the scope-disjoint analogues and the exact edges. The console is static files on one origin: it reads the persisted snapshot through the graph service's HTTP API and asks its questions through the narrator's. The only knowledge it changes is a dataset it deletes, through the graph service.

**Code** `insight_graph_service/server/app.py` (FastAPI), `insight_graph_service/server/views.py`, `sig_web_console/static/` (`index.html`; `app.js` the shell — state, vocabulary, API, health, wiring; `datasets.js`, `graph.js` (graph, sphere, table, drawer), `chat.js`, `geo.js` the surfaces; `style.css`, `vendor/cytoscape.min.js`, `vendor/plotly-gl3d.min.js`), `sig_web_console/nginx.conf`, `scripts/dev.py` · **Tests** `tests/test_ui_smoke.py`, `tests/test_sphere.py` · **Previous** [7. ## 8.1 HTTP API

The console and both APIs share one origin, routed by path:

| Path | Served by |
|---|---|
| `/api/chat/…` | the narrator (`evidence_narrator_service/app.py`): `POST /api/chat/query` (`{question, use_llm, cells?, geometry?, resolution?}`: the zone passed to `/api/search` as given, its 400 or 422 as sent) and `GET /api/chat/health` ([7.5](07_question_answering.md#75-the-language-model-and-citation-check)) |
| every other `/api/…` | the graph service (`insight_graph_service/server/app.py`) |
| anything else | the console's static files (`sig_web_console/static/`) |

In the stack the console's nginx routes them (`sig_web_console/nginx.conf`: uploads stream through up to 200 MB; the graph service gets 600 s to answer and the chat 780 s, the graph's evidence and then the LLM; Docker's DNS is asked again every 10 s, so a re-created service is found without restarting the console; static files carry `Cache-Control: no-cache`, so a browser revalidates them and picks up a rebuilt console on the next load; responses over 1 KB go out gzipped to a browser that accepts it — JSON, GeoJSON, Turtle, CSS, JavaScript and HTML, so a fine level's cell file of tens of MB crosses the wire at about a fifteenth, while uploads still stream in uncompressed). On the host, `python scripts/dev.py` composes the three on one port with the same routing and the same compression (http://127.0.0.1:8765, `WEB_HOST` / `WEB_PORT`). Run alone, the graph service (`python -m insight_graph_service.server`) serves its API only. One `Engine` serves all of the graph service's requests; batches and the Neo4j sync at start run on a single worker thread.

| Method, path | In | Out |
|---|---|---|
| `GET /api/health` | — | `{neo4j {enabled, uri, database}, embedding (the workspace's stored representation; null before the first batch), embedding_device, graph (snapshot stats), workspace, problem (why the workspace is degraded; null otherwise)}`; it runs on the event loop, so it answers while a batch runs |
| `GET /api/batches`, `GET /api/batches/{id}` | `upload_id` (query, optional) | batch records, newest first, only that upload's levels when given (404 for an unknown id); a batch reads READY once readers see its graph, PERSISTING from its commit point until then (`Engine.polled`) |
| `POST /api/upload` | multipart `file`, form `bins`, `categories` (empty = workspace defaults), `geo` (empty = a plain table; `@<r1>,<r2>` or `@auto` = one dataset per level; [2.9](02_discovery.md#29-spatial-datasets-the-geo-option)), `source`, `reliability`, `indicators` (empty = undeclared; [2.1](02_discovery.md#21-ingestion)), `table` (with `geo`: the file as a table too, its point columns left out), `supersedes` (a dataset or upload id this version replaces once READY, [6.8](06_graph_and_storage.md#68-deleting-a-dataset)) | 202 + the `UPLOADED` record of the finest level with `levels`, every level's batch id (`{"8": "B…", "7": "B…", "table": "B…"}`; `Engine.upload` returns every level's record, each with `upload_id`); processing is queued on the worker thread; 413 above `MAX_UPLOAD_MB` (`file_too_large`; the file is not kept); 400 `invalid_options` for a bad source, reliability, indicators or levels spec, or a `supersedes` that names nothing or the same file (the file is not kept) |
| `POST /api/demo` | — | 202; queues the synthetic dataset as `retail_synthetic.csv`, without options |
| `POST /api/demo/geo` | — | 202; queues the shipped California housing table as `california_housing.csv` with `geo=auto@5` and `bins=median_income_median:4` ([10.2](10_verification.md#102-the-demo-datasets)) |
| `GET /api/graph?dataset=&regions=` | optional dataset filter; `regions=1` adds the Region nodes | Cytoscape elements (`views.cytoscape_elements`): `nodes[{data: id, kind, label, full_label; Pattern: weight, direction, ptype, dataset, support, target, effect, scope[], anchor, anchor_label; Attractor: mass, n_patterns; Region: resolution, patterns}]`, `edges[{data: id, source, target, type, plane, weight, weak}]`, `stats`, `regions` (how many Region nodes `regions=1` adds) and `datasets {dataset_id: {source?, reliability, integrity}}` of every Dataset node whatever the filter. Without `regions=1` the view holds no Region node and no IN_REGION or PARENT_OF edge: 42–53 % smaller on the measured maps (the real export's 424 KB → 223 KB). With it, the Region nodes are the places of the insights in view at every level they lie at (at most five a level each) and the regions their scale chains name, each holding an insight in view (`vertical.shown_regions`; a region at an insight's own level is one of its cells); their `patterns` and label count the insights in view |
| `GET /api/nodes/{id}` | — | `{node (all props), neighbors {TYPE / "TYPE (in)": [{id, label, kind, weight, props}]}}` (`views.node_details`; 404 for an unknown id); an insight adds `dataset` (its Dataset node's props), `places` (its `vertical.places` with each edge's `share`, and `lift` and `n` for a table insight), `scale_chain` (its `vertical.scale_chain` with each region's `picture`; null for a table insight), `levels` (each step's resolution), `theme` (`{id, label}` of its `primary_anchor`, null without one) and `labels`; the IN_REGION neighbours of an insight are its `IN_REGION_SHOWN` (25) strongest by `vertical.place_key`, the other groups by weight, and `neighbor_counts` gives every group's full count (the drawer says *25 of 326*) (the headlines of the insights its credibility basis and scale chain name, of any dataset), a region adds `picture` ([7.4](07_question_answering.md#74-the-evidence-object)) |
| `POST /api/patterns/{id}/verify` | — | the insight's statistics recomputed from its stored upload (`Engine.verify_pattern`, [6.7](06_graph_and_storage.md#67-configuration-and-guarantees)): `{pattern_id, dataset_id, status: reproduced \| differs \| source_changed \| source_missing, diff [{field, journal, recomputed}], not_checked [...], detail?}`; 404 `unknown_pattern` |
| `GET /api/sphere?dataset=` | optional dataset filter | the projected sphere as data (`views.sphere_points`, [8.4](#84-the-latent-sphere)): `{points [{id, kind, xyz, hover; Pattern: cls, weight; Attractor: n_patterns}], edges [{id, type, source, target, weak}], message}` |
| `GET /api/geo` | — | the READY geo datasets: `[{dataset_id, filename, option, resolution, location, cells, points, sparse_cells, min_cell_points, base, moran_i, sac, metrics}]` (`Engine.geo_datasets`) |
| `GET /api/geo/{dataset}/cells` | — | the dataset's cell package (`geo_views.geo_cells_pack`), built once from `datasets/<id>/cells.geojson`, which its batch writes and nothing changes afterwards: `{columns, rings, scale, bbox, patterns}` — `columns` every column of the analysed cell table once, `h3` included and the `*_band` texts left out (no view reads them), a list of one value per cell row (NaN → null); `rings` one per cell row, its first vertex `[lon, lat]` to `scale` decimals and then each next vertex as integer offsets from it in 10^-`scale` degrees, `scale` 5 up to resolution 12 and 7 finer (each coordinate within half a step of the stored ring, whose vertices `cell_boundary` keeps to 6 decimals: against the H3 boundary about 0.6 m up to resolution 12 and 6 cm finer, far below a cell's edge at any resolution); `patterns [{id, rows, scope, target, effect_size, phenomenon_type, support, weight, spatial}]` (`geo_views.geo_cells`). The console rebuilds the GeoJSON features from it (`cellFeatures`). 5.4–6.0 times smaller than the file it is built from on the measured maps, 1.6–2.0 times on the wire with gzip; 404 `unknown_dataset` for a dataset without a READY geo batch (a plain table, a deleted dataset, a batch that failed after the file was written, an unknown id) |
| `GET /api/geo/{dataset}/overlay` | — | what the graph says about the map (`geo_views.geo_overlay`, derived once per commit): a GeoJSON `FeatureCollection` of the regions drawn for the dataset's insights of the dataset and of the base insights of its upload and points (`vertical.shown_regions`: each insight's places at every level it lies at, and every region its scale chain names, so every region a SCALE CHAIN or the ZONES name is drawn; none finer than the dataset's cells), each with `id`, `resolution`, the dataset's cell `rows` whose centre it holds, as events are placed (`spatial.region_features`) and its `picture`, plus `patterns {id: {credibility, integrity, scale}}`; 404 `unknown_dataset` as above |
| `GET /api/geo/{dataset}/patterns/{pattern}` | — | `{pattern_id, cells, rows, n_points, points}` — the pattern's cells and an even sample of at most `GEO_MAX_POINTS` (5000) of its points as `[lon, lat]`; for an insight of another level of the same upload (below), its footprint's cells and its own points inside them (`geo_views.geo_pattern`) |
| `GET /api/geo/{dataset}/projected` | — | the insights of the dataset's upload found at another level (the table level, another resolution) drawn on its cells, as `cells` lists its own: `[{id, rows, scope, target, effect_size, phenomenon_type, support, weight, level, spatial: {footprint_share, footprint_points}}]`, `rows` the cells it is drawn by: for an insight of another geo level every cell inside its own, through the cell centre (`spatial.cells_inside`, as a zone is placed, so a coarser insight keeps its whole extent), for a table-level insight the busiest cells that together hold `GEO_FOOTPRINT_SHARE` (0.8) of its located points (`spatial.footprint`); `footprint_share` is the share of its located points those rows hold, `footprint_points` their number. Only a level of the same `upload_id` whose rows index the map's points takes part: a matching row count alone links nothing. Derived once per commit (`geo_views.geo_projected`) |
| `GET /api/geo/{dataset}/window?bbox=w,s,e,n` | `bbox` in degrees | the map as a window on the graph (`geo_views.geo_window`): `{cells, points, first, insights, themes [{id, label, insights [{id, label, level, values, target, effect, ptype, weight, points, share, cells, lift, also [{id, level}]}]}]}` — the upload's insights characteristic of the cells whose centres lie in the box ([8.7](#87-the-map)), under their theme (the strongest non-weak ACTIVATES, `graph.primary_anchor`); `points` an insight's located events in view, `lift` their smoothed over-representation there; a box with `west > east` crosses ±180°; 400 `invalid_options` for a box that is not four numbers in degrees with south ≤ north |
| `GET /api/export/geosparql.ttl` | — | the committed graph as RDF Turtle with GeoSPARQL geometries (`text/turtle`; [6.9](06_graph_and_storage.md#69-rdf-export)); 409 `workspace_degraded` on a degraded workspace |
| `POST /api/search` | `{question, cells?, geometry?, resolution?}`: a map zone as H3 cells or as GeoJSON, `{center: [lon, lat], radius_m}` or `{bbox: [w, s, e, n]}`, and the finest dataset resolution it weighs ([7.2](07_question_answering.md#72-seeds)) | the `EvidencePayload` of the question ([7.5](07_question_answering.md#75-the-language-model-and-citation-check)); 400 for an empty question without a zone, for both `cells` and `geometry`, and `invalid_options` for a zone that cannot be read |
| `PATCH /api/datasets/{id}` | JSON `{source?, reliability?, indicators?, supersedes?}` (absent = unchanged, `""` = undeclared; `indicators` replaces the whole registry; `supersedes` deletes the dataset or upload it names in the same transaction) | `{dataset_id, source, reliability, indicators, supersedes, superseded?, neo4j}` after the snapshot is recompiled ([6.2](06_graph_and_storage.md#62-the-graph-schema)); 404 for an unknown or not READY dataset, 400 `invalid_options` for a bad value, an indicator for a metric the dataset does not have, or a `supersedes` naming nothing, the dataset itself or its own upload; 409 `busy` while a batch of the target is still to run, 409 `metadata_mismatch` for a dataset whose batch record fails its metadata digest ([6.7](06_graph_and_storage.md#67-configuration-and-guarantees)) |
| `DELETE /api/datasets/{id}` | — | removes the dataset from the knowledge base ([6.8](06_graph_and_storage.md#68-deleting-a-dataset)): `{dataset_id, datasets, batches, patterns_removed, anchors_removed, neo4j}`; 404 for an unknown id, 409 while one of its batches runs |
| `DELETE /api/uploads/{upload_id}` | — | removes every level of one upload in one transaction: `{upload_id, datasets, batches, patterns_removed, anchors_removed, neo4j}`; 404 `unknown_upload`, 409 while one of its batches runs |
| `POST /api/reset` | — | deletes the workspace and, with `NEO4J_ENABLED`, clears the mirror: `{status: "reset", neo4j}`; 409 at once, without waiting, while a batch or a deletion runs or an upload waits; also the way out of a degraded start |

**Refusals.** One exception handler turns every refusal of the engine ([9.4](09_operations.md#94-error-codes)) into the body `{detail, code}` with the status of [12.4](12_architecture.md#124-services-and-contracts). An unknown batch or node is a plain 404 `{detail}`.
- **An empty graph is no error.** The read routes return empty elements, and `/api/search` returns the empty payload.
- **A degraded workspace** ([6.5](06_graph_and_storage.md#65-versions-degraded-start-and-reset)) serves the empty state on the read routes and names its reason in `/api/health` (`problem`). Upload, demo, search, the RDF export, the map routes (`/api/geo…`) and deletion answer 409 `workspace_degraded` until `POST /api/reset`.
- **A representation fingerprint** other than the workspace's refuses `/api/search` with 409 `representation_mismatch` and fails a batch at EMBEDDING.
- **A sphere that cannot be drawn** answers 200 with no points and a `message`: no insights yet, or fewer than four points (insights + themes).

## 8.2 The single-page UI

Plain HTML, JavaScript and a design-token stylesheet with light and dark themes; no framework. Cytoscape.js 3.30.2 draws the graph and plotly.js 3.6.0 (its `gl3d` partial bundle) the sphere; both are vendored in `sig_web_console/static/vendor/` (`sig_web_console/PROVENANCE.md`), so the console loads nothing from a CDN and works offline. It reaches both services through relative `/api/` paths on its own origin.

* **Top bar** — health pills: the LLM (reachable / model found, from `GET /api/chat/health`), the Neo4j mirror on or off and the embedding model and device (from `GET /api/health`; the device `cpu` is amber, its tooltip pointing a Mac to the host run with MPS and an NVIDIA host to `compose.gpu.yaml`, README *Mac: GPU*), refreshed every 30 s and after each READY batch; *Server unreachable* when `/api/health` fails. A theme toggle (remembered in the browser).
* **Datasets rail** (left) — a drop zone for CSV, TSV, TXT and Parquet files; *Column options*: *Treat as categories* (`categories`), *Split numbers into bands* (`bins`), *Spatial analysis* (`geo`, its example `auto@auto`) with *+ a base level without geography* (`table`, ticked by default and enabled once `geo` has a value, a value the browser restored included: one submit makes the geo levels and the table level of the file), *What the metrics measure* (`indicators`), *Source* and *Source reliability* (`source`, `reliability`: A–F, *Not stated* by default); *Analyse*, *Demo: table* (the synthetic retail orders) and *Demo: map* (the housing block groups as H3 cells). One card per dataset (its READY batch, otherwise its latest attempt), named by its file and, for a geo dataset or the table level of a geo upload, its level (`points.csv · H3 r7`, `points.csv · table`), as are the dataset filter's options and the delete confirmation: the levels of one upload are datasets of one file. The cards of one file's levels (its geo levels and its table level, under one `upload_id`, later uploads of the same bytes included; a plain upload of them is no level and stands alone) stand together in the order the levels run, finest first and the table last, under a line naming the file and how many of its levels are ready, without findings and failed: the others stand on their own ([9.1](09_operations.md#91-the-batch-lifecycle)). A geo level that found nothing to mine (a code of `uploads.EMPTY_LEVEL`: `invalid_schema`, `no_numeric_targets`, `no_candidates`, `no_viable_insights`) beside a READY level of its upload is a normal result of that level, not an error: its card is neutral, *No findings*, with the reason. An upload none of whose levels is READY failed, as the backend reads it (`uploads.replaced_by` applies no `supersedes`), so its cards stay a red *Failed* with their tips, as do a table level's and a plain upload's. While running: a progress bar, the stage in plain words and how long it has run, from the record's `stage_times` ("Searching subgroups… step 4 of 10 · 1 min 12 s", ticking each second between polls). Below the date the card shows what the graph trusts of the dataset — its Dataset node, from `GET /api/graph`, never the batch record: a declared source or rating as a chip `<source> · <reliability>`, *metadata failed its check* (red, no source) when the record no longer matches its metadata digest, *metadata unverified* for a record written before digests ([6.7](06_graph_and_storage.md#67-configuration-and-guarantees)). When READY: insights, themes first learned from it and rows, then columns, subgroups tested, filtered out, duration and dimension tags. When FAILED: a plain-language title, the cause and a tip per error code (for `no_candidates`: mark number-coded columns as categories). Clicking a READY card focuses all three views on that dataset — the dataset → insights → themes chain is the same filter everywhere: the views reload when the READY batches or the filter change, from one place (`refreshBatches`), the map beside the graph rather than after it. The latest request wins: the graph of a filter left before it answered is dropped (`loadGraph`), as are the points of an insight clicked before the next one (`GeoMap.focusPattern`); the map refreshes one pass at a time, and a refresh asked during a pass runs one more after it, so it reads the filter as it is then (`GeoMap.refresh`). A **Delete** button at the foot of every finished card — READY, FAILED or SKIPPED; disabled, with a tooltip, while any batch runs, since a deletion waits for it — asks for confirmation and calls `DELETE /api/datasets/{id}` (the batch id for an upload that failed before it had a dataset id): the backend removes the dataset ([6.8](06_graph_and_storage.md#68-deleting-a-dataset)) and the rail and the views reload from it, so what is shown is always what is stored. The rail polls every 2.5 s while a batch runs (every 3 s after a failed poll) and reloads the views when one becomes READY. A poll replaces only the cards whose markup changed, a group's levels one by one (`renderRail`), and rewrites the filter's options only when the READY set changes, so a stage change replaces the running card alone and an open filter list, a click on another card or level and its *Delete* survive the poll: over 10 s of a level running beside a READY level of its upload and a READY table, with one stage change, 4 polls replace 1 READY card (its *Delete* disabled as the batch starts) and rewrite the filter once (the new level's option), against 12 polls, 23 READY cards and 12 filter rewrites at 0.9 s with a full rewrite. While the workspace is degraded ([6.5](06_graph_and_storage.md#65-versions-degraded-start-and-reset)) the rail shows the reason from `GET /api/health` and a *Reset workspace* button, which asks for confirmation and calls `POST /api/reset`.
* **Canvas** (centre) with the view tabs **Graph | 3D Sphere | Insights** — three views of the same analytical state —, the dataset filter, the graph's layout selector (*Two planes* / *Force*), *Fit* (fits the graph, resets the sphere camera), *Legend* (shows or hides the legend column; remembered) and *Clear highlight*, the console's one action that clears an answer: its highlight in the graph and on the sphere, the map's focus, evidence and cell popup (`clearAnswer`). Left of the view sits the **legend column** ([8.3](#83-one-visual-language-for-the-graph-and-the-sphere)), the same for all three views: a caption (`52 insights · 7 themes in view`), the node classes, the link layers as switches and the answer markers, each with its count in the current view (the answer counts appear after a question). Hovering an entry spotlights its elements — the rest dims, in the graph and on the sphere.
* **Columns** — the borders between the datasets rail, the canvas and the chat can be dragged (rail ≥ 220 px, chat ≥ 300 px, the canvas keeps ≥ 380 px); widths are remembered in the browser, and a double-click on a border resets it.
  * *Graph* — the *Two planes* layout puts themes in a top row ("THEMES"), ordered by a greedy chain over theme links (RELATED_TO or CO_OCCURS) so that linked themes sit side by side, with RELATED_TO as arcs labelled by weight and CO_OCCURS as dashed lines; insights sit below ("INSIGHTS"), grouped under their strongest theme; Dimension and Metric nodes form a bottom row when the *Columns* layer is on. A *Force* layout is also available; switching layouts keeps the elements, the layer state and the highlight. No Region node takes part in the force layout: the regions stand in rows by level under its nodes, each under the insights (or the finer regions) it holds and 70 px from the next (`regionRows`, the rows of *Two planes* too), so the regions switch never re-runs it — 22–58 ms in the force layout and 28–86 ms in *Two planes* on the measured maps, the first switch fetching them, against 0.4–0.9 s in the force layout when the regions were laid out with the rest.
  * *Insights* — a sortable, filterable table (where, metric, effect, rows, evidence, theme); a row opens the details drawer.
  * *3D Sphere* — [8.4](#84-the-latent-sphere), drawn in the page by plotly.js and as interactive as the graph: the legend's switches show and hide its link layers in place (Columns is disabled there: column nodes have no vectors), hovering a legend entry spotlights it, a click on an insight or a theme opens the same details drawer, evidence cards isolate their path; rotate, zoom and hover as usual, *Fit* resets the camera.
* **Map** (a fourth tab, shown once a geo dataset is READY; `sig_web_console/static/geo.js`) — [8.7](#87-the-map).
* **Details drawer** (node click, table row, citation or neighbour) — an insight opens with a one-sentence reading of its target ("discount is higher here — median 19.19 vs 10.74 overall (+2.21 sd)"), the shifts with meters and the evidence facts (rows and share, evidence weight, adjusted p, bootstrap stability, correlation change, confounders, aliases), then *Trust*: the source and its reliability (from the Dataset node; *unknown* when its metadata failed its check), the credibility level in words with its sources and whether it was compared by place or by theme and metric, a collapsible *Basis* listing the insights that confirm or contradict it (clickable), and the integrity of its statistics. A geo insight adds *Scale*: the scale label and its scale chain as clickable rows, ↑ the coarser and ↓ the finer levels of the same phenomenon (*same shift* / *opposite shift*), then the regions above it with what each holds; a table insight placed by its map adds *Where* in its stead: its places, each with its share of the insight, its lift and its events. *Re-check from the raw data* (`#verify-btn`) asks `POST /api/patterns/{id}/verify` and shows the status, the fields that differ and what is not recomputed. A correlation-change insight leads with its correlation change, lists its median differences as *not validated*, and shows p as *not tested* and stability as *not measured*. Below come the collapsible *Score breakdown* (weight factors, SD, EMM, volume), *Canonical representation* and *Provenance* (dataset, batch, selector, engine, rows reference, embedding spec). A theme shows its signature and mass, evidence mass and dispersion; a map region its resolution, what it holds (insights, datasets, themes) and the cells covered. Connections are grouped under plain names ("Belongs to theme", "Narrower insights", "Contrasts with", "Insights in this region", "Sub-regions", …) and are clickable (the drawer follows; with the map open, one the map draws is focused there); a *Same place* partner names its relation (*zones overlap*, *zones touch*, *same region, zones apart*).
* **Chat** (right) — a welcome card whose suggested questions follow the data that is there: none without a dataset, each demo dataset's own set (`SUGGESTIONS` in `app.js`, by filename), any other geo dataset's questions from its insights ([8.7](#87-the-map)), narrowed to one dataset by the dataset filter; user and assistant bubbles; a typing indicator while the graph is searched, with how long the question has waited and *Cancel*, which aborts the request and frees the question box at once; the answer rendered from light Markdown (headings in either script) with clickable `[P#]` citations (grouped `[P1, P3]` too; the pattern id is in the tooltip) that open the drawer; chips for the model and latency (or "Evidence only"), "n sources cited" (or "No citations" when the check failed) and the cross-segment count; an *Understood: маржа → margin · телефонів → phones* line when words of the question were grounded onto data literals ([7.1.1](07_question_answering.md#711-literal-grounding)); then three panel tabs, all closed until clicked (a click on the open one closes it again; an open one stays open as the next answers arrive): **Evidence & how it was found** — a transversal-check line and one card per item (key, role badge *match* / *lattice* / *via theme* / *coarser level* / *finer level*, an *other segment* badge, an *also* badge naming the other levels of the same finding — their own cards are not shown —, *in the asked area* or *outside the asked area* for an item of a level the zone weighed (`view.evidence.area`, [7.4](07_question_answering.md#74-the-evidence-object)), its scale label (*regional*, *scale dependent*, *not found coarser*), scope, the top two shifts — for a correlation-change insight its relationship instead —, rows, evidence, the trust badges *source B · credibility 6 · integrity ok* when the item has a trust line (its full text, the line the model saw, in the tooltip), path chain, and for a host of a scale chain its levels `res 7: P1 +1.60 sd → res 5: P7 +1.10 sd → region …`), preceded by the *Zones* of the evidence (`view.evidence.zones`, each with what it holds) and its *Notes* —, *Sources* (the provenance footer) and *Prompt* (the exact evidence the model saw). Follow-up suggestions are derived from the evidence (the first theme, the first cross-segment item, the seed's correlation pair). A notice above evidence-only answers comes from `answer_mode` / `llm.error`, never from the answer text; a red one names every evidence dataset whose metadata failed its check. Enter sends, Shift+Enter breaks a line; *New chat* empties the thread and clears the answer as *Clear highlight* does, and aborts a pending question: an answer that still comes for a turn no longer in the thread paints nothing; a switch turns the LLM explanation off. A question goes to `POST /api/chat/query`; the console reads the answer's own fields (`answer`, `answer_mode`, `llm`, `citations`, `prompt`, `provenance_footer`) and the graph service's `view` passed through by the narrator (evidence cards with the parse, traversal baselines, highlight groups).

  **Language.** The application chrome — navigation, tabs, buttons, labels, legend, drawer, table, status texts — is English. The chat's natural language is Ukrainian: the suggested and follow-up questions, the model's answer (system prompt rule 9, [7.5](07_question_answering.md#75-the-language-model-and-citation-check)), the evidence-only summary and the transversal-check note. Every data literal stays exactly as the data holds it, in its own script — column names, values, dataset names, ids, `[P#]` keys: *"Чому margin нижчий для phones у US?"*, never a translated or transliterated `margin`. The parser matches those literals as typed and reads the Ukrainian direction and relationship words by stem ([7.1](07_question_answering.md#71-from-question-to-query)), so a Ukrainian question retrieves exactly what its English twin does.

## 8.3 One visual language for the graph and the sphere

The graph and the sphere are two projections of one snapshot, so one meaning has one label and one marker in both. The legend column is that contract, and its link entries are the layer switches for both views: a switch restyles the sphere's traces in place (`Plotly.restyle`), without a new projection. One key ties the three sides together: a legend entry's `data-key` in `index.html` names its graph selector in `app.js` (`MARKS`, and `LEGEND` with the answer markers; the counts come from the same selectors) and is the `meta` of every sphere trace it explains (`sphereTraces`) — display names join nothing. By default **Hierarchy**, **Theme links** and **Memberships** are on. Colours are the theme tokens of `style.css`; the sphere reads the same tokens at every draw (`spherePalette`), so it follows light and dark mode.

## 8.4 The latent sphere

The graph service projects and the console draws. The projection is lac's prosphera projection (`views.project_to_sphere`, the same scikit-learn calls; no projector is vendored and prosphera is not a dependency), fed with insight vectors and anchor centroids instead of text chunks and concepts. On the stacked matrix `[P ; A]` (one frame, one commit):

```text
per-feature robust scaling (median, IQR over the 5–95 % quantile range)  →  KernelPCA(kernel = cosine, 3 components)
→ centre by the mean  →  u = y / ‖y‖,  radius = minmax(log ‖y‖²) ∈ [0.1, 1]
```

Points lie inside the unit ball: the direction comes from the kernel PCA, the radius from the (log) spread. The kernel PCA's random state is `RANDOM_SEED` (42), so one commit always projects the same way. `views.sphere_points(state, seed, dataset)`, behind `GET /api/sphere`, takes the patterns — of one dataset when the filter is set, so the projection is refit on the subset — and the anchors they activate. It returns every placed point with its id, kind, class (`up`, `down`, `cov`) and evidence weight or member count, its coordinates and its hover text, plus every edge whose two ends are placed (the lattice edges, ACTIVATES with its `weak` flag, RELATED_TO and CO_OCCURS). An insight's hover names its primary theme (`views.primary_anchor`, its strongest membership) and the alignment.

The console (`sphereTraces` in `graph.js`) draws it in the graph's language ([8.3](#83-one-visual-language-for-the-graph-and-the-sphere)):
- one trace per insight class and per link layer, each tagged with its legend key as `meta` and starting with the visibility of its toggle;
- the themes as labelled diamonds;
- six faint half-axes and three great circles for depth;
- with a highlight, the answer-path lines and the seed, evidence, other-segment and themes-visited rings.

The drawing has no title and no Plotly legend of its own — the legend column explains it — and its colours are the console's theme tokens. Membership proximity, not colour, shows which theme an insight belongs to; hover text names the theme and the alignment.

The console fetches the projection once per graph and dataset filter. An answer, an isolated path or a theme change redraws the traces from it (`Plotly.react`, the camera kept) without a new request; layer switches and the legend spotlight restyle the live traces. Every insight and theme point carries its node id (`customdata`), which is how a click opens the drawer. Three dimensions cannot preserve 1152-dimensional cosines: visual closeness on the sphere is a hint, the stored cosines are the truth ([5.7](05_latent_anchors.md#57-links-between-anchors)).

## 8.7 The map

The **Map** tab draws the H3 cells of a geo dataset ([2.9](02_discovery.md#29-spatial-datasets-the-geo-option)) with MapLibre GL JS 4.7.1 over an **offline** basemap of two boxes, Ukraine with its neighbours and California (the map demo's area): country borders (Natural Earth 10m, the Ukrainian point of view), first-level boundaries, rivers, lakes, populated places with their Ukrainian names (`sig_web_console/static/vendor/geo/`, `PROVENANCE.md`) and a one-degree graticule over the whole globe. Outside the two boxes the cells lie on the graticule alone. Nothing is fetched from outside the console's origin. The map keeps its dark tactical palette in both themes. It shows the dataset chosen in the dataset filter when that one is a geo dataset, otherwise the first one. It reads that dataset's cells, insights of other levels and overlay only once its tab is open (`GeoMap.show`): until then the console reads `/api/geo` alone, for the tab and the map's dataset (`GeoMap.current`), and a commit while another tab is open is applied when the map opens. The welcome card's questions for a geo dataset come from the graph's insights of that dataset (`GeoMap.suggestions` over `S.nodes`), so they need no cell loaded.

* **HUD** (top left) — the file, resolution, cells and points, and the SAC line `significant without → with the n_eff correction`; *Colour cells by* any numeric cell column (seven quantile classes; NaN cells stay dark); layer switches *Cells*, *Hot / cold spots* (glowing outlines of `lisa_points`), *Events*, *Borders*, *Places*, *Regions*.
* **Regions** — the regions drawn for the dataset's insights (`GET /api/geo/{dataset}/overlay`) as teal dashed outlines, each with its insight count across every dataset at its centre, one level at a time: the listed region level nearest to the zoom minus 3 (zoom 6 → resolution 3, zoom 8 → 5), so zooming in steps down the region levels as `ZONES` and the scale chain do. The drawn level stays until another fits better by half a zoom step, so a zoom near a threshold does not flip it, and the next coarser level is outlined pale beneath it, so stepping onto a sparse finer level never leaves an empty map. The counts are a symbol layer of icons drawn once per count on a canvas (the offline basemap has no glyphs), not DOM elements; the level changes when a move ends, not on each of its frames. The overlay is fetched again after every commit, so a second source's confirmation shows without a reload; one that cannot be read says *Regions and trust unavailable* under the map's meta line instead of drawing no regions. The insights of the upload's other levels (`/projected`) are fetched with it; when they cannot be read, *Insights of other levels unavailable* says so on a line of its own, and the map keeps its own insights. Every region a scale chain names is drawn: the regions coarser than its top insight, walked up from the region its last step up met in, or from the insight's home region when it has none (level 7 for cells at 8; an insight at a region level starts at the next coarser one, since a region at its own level is one of its cells); an answer's `ZONES` stay in the evidence pane, and every region they name is among those drawn: the ZONES and the overlay take an insight's places from the same `vertical.places`. A region finer than the map's cells is not drawn on it. Place names are DOM markers, at most 40: the most populous ones in view above the zoom's population floor, chosen again when a move ends.
* **An answer** paints nothing and moves no camera: the map stays on its dataset when it draws one of the answer's insights (its own, or one of another level of its upload, the table level included), else switches to the answer's geo dataset, and waits. A citation `[P#]` or an evidence card clicked in the chat while the map is open focuses that insight instead of the graph: its cells painted — orange where its target is higher, cyan where lower, green for a correlation change — the rest dimmed, the view fitted to it. Another click focuses another insight; the card's ×, Esc, *Clear highlight* or *New chat* removes the focus. Esc closes one layer a press — the cell popup, then the map's focus, then the details drawer — and leaves a text field it is pressed in alone (a checkbox or a select keeps it working).
* **Focus** — a pulsing amber outline on the insight's cells, drawn from a source holding only those cells (as the zone's outline is: the cost follows the cells painted, and loading a dataset clears both) (about 15 steps a second; it holds still while the map moves, until the map is idle again, and while the map is out of sight), its points (`GET /api/geo/{dataset}/patterns/{pattern}`) as glowing dots, and a card: key, scope, shift, cells, compactness, points, `n_eff`, Moran's I, weight, and the retrieval path; an insight whose record fails its digest is tagged *integrity mismatch* there, as in the cell popup.
* **IN VIEW** (top right) — the themes and insights of what the map shows (`GET /api/geo/{dataset}/window`), read again 250 ms after the map stops moving (a later view's answer wins): the insights of the dataset's upload — its own, and those found at another level of the same file, the table level included, drawn as `/projected` draws them — characteristic of the view, under their theme, the three leading themes open; each row names its level (`+n` when `n` other levels restate it, named in its tooltip), scope, shift and lift (×). The list waits while a dataset loads, and a full view of a dataset is fitted clear of the open list, so the window's box holds all its cells. A click focuses the insight without moving the camera and adds its card to the chat: the scope and the shift in words, its theme — `primary_anchor`, as `GET /api/nodes/{id}` names it (`theme`) and the list shows it, never a weak membership; a click opens the drawer and the theme in the list —, *Walk on* to its scale chain's levels first (`↑ res 5: …`, `↓ res 7: …`, same or opposite shift; `levels` names their resolutions) and then its CONTRASTS, SPECIALIZES, SIBLING and CO_LOCATED neighbours (one drawn on this map is picked there, another clears the focus and opens in the details drawer, which says it is not on this map; the list holds intact insights only, and an insight reached by *Walk on* whose record fails its digest is tagged *integrity mismatch* on its card), *Запитати граф про це* — the question asked with the insight's place, the H3 ids of the cells this map draws it by as the zone, in place of a zone selected on the map ([7.2](07_question_answering.md#72-seeds); the chat line says *зона на карті*), so its answer carries the AREA line and the insight seeds it with a place — and *Показати в графі*, which first clears a dataset filter on another dataset, since the graph would not hold the node under it. A citation of an insight of another level of the upload paints its footprint. A map narrower than 800 px starts with the list folded. The insights of the other levels are drawn on read, once per commit (`geo_views._projection`).

**What the window lists** (`geo_views.geo_window`). The box holds the map's cells whose centres lie in it (`window_view`; `west > east` is a view across ±180°, which the console sends when the map shows the antimeridian, and `-180…180` when it shows the whole world). An insight counts all its located events, never only the cells it is drawn by: a geo insight's are the points in its cells, a table-level insight's its member rows that have a cell, each once. With `|P_loc|` those events, `x` of them in view, `N` the map's located points and `n_V` those in view, `E = |P_loc| · n_V / N` is the number its map-wide share puts in view, and

`lift = (x + a) / (E + a)`, `a = WINDOW_LIFT_PRIOR` (30)

lists an insight with `x ≥ link_min_events(|P_loc|)` — the events a base insight needs in a region, `min(GEO_LINK_MIN_EVENTS (30), max(5, ⌈0.05 · |P_loc|⌉))` ([6.1](06_graph_and_storage.md#61-the-structural-plane)) — and `lift ≥ 1`, so a view of fewer than 5 points lists nothing; a base insight the graph leaves unplaced (`geo: partial`) is not listed. The whole map gives every insight `x = E`, lift 1, a table-level insight with unlocated events too (`|P_loc|` counts located events only). `a` is a pseudo-count of events at lift 1: an insight needs about `a` events in view before its own count weighs as much as the prior, so a handful of events far from where the map expects them cannot lead the list, and `E + a` is never 0. Measured on the views of three maps (40 views at each of five scales): among the five leading rows ranked without an event floor, the share with fewer than 30 events falls from 3–11 % at `a = 0` to a plateau of 1–5 % from `a` ≈ 20, and stays there to 100; 30 is on the plateau and equals the region link's floor. A row's `cells` counts the cells holding its events in view; a geo insight of another level is drawn by the cells inside its own (through their centres), so its `footprint_share` in `/projected` is the share of its events those cells hold, 0.95–0.99 on the measured maps (a boundary cell's points can lie in a map cell whose centre is outside it). One result found at several levels lists once (`also`, `_fold_levels`): hosts are the open dataset's insights, then the finest levels, and each folds the listed levels its scale chain restates (`vertical.restating`: every step so far corresponds, the same upload, the rule that folds levels in an answer, [7.4](07_question_answering.md#74-the-evidence-object)); a level several hosts restate goes to the one whose subgroup is closest to its own (`vertical.affinity`, the Jaccard overlap of their conditions), the earlier on a tie. Hosts follow which levels a view lists, never its numbers, so the same rows keep one host from view to view; a level folded where its host is listed stands alone in a view without it. Which levels lead follows the view's extent (`first`): over more than `WINDOW_DETAIL_REGIONS` (3) regions of `WINDOW_DETAIL_LEVEL` (5) — on a map coarser than 5 its own cells, each counted as the seven-fold area it covers per level — the table and the coarser levels come first (`coarse`), closer the map's own and finer (`map`); then by lift. Themes follow their leading row under the same order, not their best lift alone, so a wide view leads with the themes of its coarse findings; the insights without a theme come last. On the three maps the switch falls between 1/16 and 1/64 of the map's extent. A view answers from the commit's memo: p95 0.9–3.6 ms over HTTP on the measured maps, the first view after a commit 14–173 ms (it builds the projection and the levels' chains).
* **A cell click** opens a popup, one at a time (a focus, a dataset load, another tab and Esc close it, so a click on one of its insights shows that insight's card): the cell id, its LISA class, every non-null cell column, the insights covering it (most weight first, each with its credibility and scale label; a click focuses one) and the region of the drawn level holding the cell, with what it holds (insights, datasets, themes). *+ Додати до зони* (or a Shift-click on the cell) adds it to the **zone**, outlined in white dashes; the **zone bar** (bottom right, *ZONE · n cells*) asks about the zone with the text typed in the chat box, if any (*ASK*), or clears it (✕); while a zone is selected, every question carries it — the chat box, Enter and the suggested questions too — until ✕ clears it. *Запитати про цю зону* asks about the zone when it holds the cell, else about the cell alone. The question carries the cells (`cells`), so the answer is the ordinary search weighted by the zone ([7.2](07_question_answering.md#72-seeds)); the chat shows *зона на карті · комірок: n* under it, and the zone stays for the next question and across datasets (H3 ids are global): a map of another level, which does not draw the zone's cells, says how many it holds (*ZONE · 4 cells · 3 on this map*), and the graph service places the cells on that level by their centres ([7.2](07_question_answering.md#72-seeds)).
* The cursor line (bottom left) shows coordinates, zoom and the cell under the pointer; the welcome card of an empty chat and the follow-ups after a geo answer offer questions in everyday words, without column names: the hottest zones (when the dataset has hot spots), where a category value occurs more often (the strongest share insight), where events are fewest (when an insight has a quietest-quarter neighbourhood), and zones that look alike in different places.
