Канон для сценаріїв, правил простору й часу, межі POC і порядку реалізації; реалізацію M17 описує [`cross_type_context_architecture.md`](cross_type_context_architecture.md) (далі — спека M17), і цей документ її не переказує, а посилається. ## 1. Стан після M17: що система вже вміє

Базова одиниця обробки — **датасет** = одне читання одного збереженого файлу з опціями (`dataset_id` — відбиток байтів і опцій, `subgroup_miner/ingestion.py::dataset_fingerprint`), яке проходить один конвеєр: читання → (для гео) таблиця комірок H3 → профіль → пошук когорт → валідація → відбір → вектори → онтологія → граф → знімок (docs 09 §9.1) **[факт]**. Гео-завантаження з `@auto` стає одним датасетом на кожен рівень H3 під спільним `upload_id` **[факт]**.

Крос-типовий контекст M17 **[факт, спека M17 §2–§6, §15]**:

| Можливість | Де | Що саме |
|---|---|---|
| шар іншого типу як умова | `subgroup_miner/context.py`, `spatial.build_cells(context=)` | точки другого файлу порахувано на сітці цілі як одна примусова смуга `context_<шар>_band` (`none nearby \| q1..q4`) по диску `context_ring` 0/1/2 — опція завантаження, у відбитку лише нетипова; шар названо від стовбура файлу (`chicago_bars.csv` → `context_chicago_bars_band`) |
| захист від спільної щільності | `discovery._context_evidence`, `selection.py` | нуль перестановок у батьківських комірках: `p_context`, поправка Бонферроні на когорти з умовою шару, зупинка марності, шари скоупу роздаються однією перестановкою; відмова `context_confounded`; `verify` відтворює |
| межа комбінаторики | `uploads.MAX_CONTEXT_LAYERS = 2` | не більше двох шарів на прогін — виміряно (спека M17 §14.6: сім'я ×25 з двома шарами; 3-кон'юнкції зникають з п'ятим) |
| контекст у завантаженні | `POST /api/upload` + `context`/`context_demo`/`context_geo`/`context_ring` | шари як додаткові файли того самого завантаження |
| «лише шар» | `POST /api/upload` + `layer=true` → `uploads.store_layer` | файл збережено, точки знайдено раз, один запис `LAYER` (термінальний), нічого не майниться |
| прогін між збереженими | `POST /api/crosstype {target, layers, ring?, levels?}` → `Engine.cross` → `uploads.cross_runs` | ціль читається знову на найдрібнішому рівні та рівнях, на яких читали кожен змайнений шар; копії файлів шарів; опції й довіра цілі успадковані; допускаються лише інсайти зі смугою шару (`outside_cross_type`); повтор — `SKIPPED` за відбитком |
| консоль | `datasets.js`, `index.html` | *Лише шар*; панель *Крос-типовий аналіз* (ціль, шари ≤ 2, рівні цілі з галочками за правилом сервера, радіус, «і навпаки»); картки `<файл> · H3 r<k> · + <шар>` у групі цілі |
| дані в git | `data/demo` | `chicago_crimes` (2025, з `district`, без табличного рівня), `chicago_crimes_2024`, `chicago_bars` (3 037), `chicago_liquor_stores`, `chicago_l_stations`, `chicago_schools`, `chicago_crashes` |

Виміряно (спека M17 §14) **[факт]**: злочини `@9`, диск 1, шар барів — тест медіани сам допускає 11 крос-типових знахідок (19 разом із магазинами), нуль — **0**: усі — зсуви складу злочинів (частка шахрайства, крадіжок, наркотиків/зброї), які відтворюються розкладом закладів у межах батьківських комірок, тобто землекористуванням. Станції 'L' — нуль допускає 1 (частка шахрайства біля станції; відтворюється на 2024). Частотні гіпотези літератури («більше грабежів біля барів») не виражаються: частота є лише загальним `points`, який правило тавтології переказує на гарячих точках; відкриті питання спеки M17 §13 — лічильник на тип події (= сценарій S4 тут) і `@10` з радіусом 0.

Шар барів — поточні ліцензії порталу: у експорті лише ідентифікатор, вид ліцензії і точка; **періодів чинності не постачається** (у джерелі є дати терміну) **[факт, `scripts/demo_data/chicago_bars.py`]**.

## 2. Обмеження реалізації, виявлені дослідженням (2026-11-01, три незалежні прочитання коду)

1. **Фільтра рядків у читанні немає** — `load_dataset`, `read_file`, `_to_cells`, `point_profile`, `read_context` читають файл цілком; поділи роблять скрипти, записуючи нові CSV (`crosstype_validation.py:80`) **[факт]**. `upload_id` — sha байтів файлу (`uploads.upload_id`), і всі групування «рівнів одного читання» ключовані лише ним: `cross_runs`, `same_points`, `upload_levels`, ланцюг масштабів, `delete_upload`, `supersedes`, групи карток **[факт]**.
2. **Час на гео-рівні входить у пошук, але не як вікно.** `build_cells` робить з кожної дато-подібної колонки метрики `<col>_active_days`, `<col>_late_share` і примусову смугу `neighbours_<col>_active_days_band` (`spatial.py:423-434, 468-480`); траєкторії й періоди — після допуску; у вікні часу ніщо не майниться — свідоме рішення (docs 02 §2.10) **[факт]**.
3. **Спани двох датасетів ніде не порівнюються**; час шару не читається (`read_context` знаходить лише точки); прогін успадковує `time/grid/tz` цілі **[факт]**. Змайнений подієвий датасет як шар читається статично за весь свій період — мовчки **[висновок]**.
4. **Версії й видалення.** `supersedes=<upload_id>` видаляє всі батчі цього `upload_id` — і прогони цілі (у них її `upload_id`); `check_target` приймає лише ідентифікатори з READY/SKIPPED батчем — **завантаження «лише шар» не можна замінити**; видалення завантаження шару лишає прогони цілими (копії файлів); поняття похідного/застарілого датасету немає; єдина перевірка — `verify` на вимогу **[факт]**.
5. **Рівні.** `@auto`: найдрібніший з r10…r3, що має ≥ 50 щільних комірок, ≥ 0.5 точок у них і ≤ 5 000 комірок за капом; грубші — лише `GEO_REGION_LEVELS` (7, 5, 3, 1) з ≥ 500 комірок, усього ≤ 3; явні грубші рівні теж лише регіональні **[факт, `spatial.select_levels`, `uploads.resolve_levels`]**. Вхід — лише точки; полігони не підтримуються **[факт]**.
6. **Граф.** Єдиний міждатасетний зв'язок інсайтів — `CO_LOCATED` (`overlaps ≥ 0.3` / `adjacent` / `same_region`, по 3 партнери на бік); спільні вузли регіонів, часу й тем. `SHARES_REGION` і `EVOLVES_TO` не існують. **Граф не знає, що прогін побудовано з цілі й шару**: знімок копіює лише `upload_id`, `level`, `supersedes`; поля `cross` і `context` запису не підписані й ніким у графі не читаються **[факт]**. Прогін — «брат» цілі: те саме завантаження і джерело → `CO_LOCATED` з інсайтами цілі на тому ж рівні, довіра рахує їх одним джерелом **[висновок]**.
7. **Консоль і доказ.** Запитання беруть зону, період і `as_of` — терміна «датасет» немає; фільтр датасету керує лише видами. **Відмови пишуться в `rejections.json`, але не віддаються й не показуються** (картка показує лише `pruned_total`, хоча `metrics.pruned {причина: n}` уже приходить у `GET /api/batches`); **попередження батча не рендеряться**; **`p_context` і `context_family` не показуються ніде** (ні шухляда, ні картка мапи, ні рядок довіри); смуги не малюються на мапі; українська фраза смуги жорстко каже «комірка й сусідні» — хибно для радіуса 0 і 2; готовий `context_only` набір не зберегти шаром з консолі (сервер приймає `demo=<key>&layer=true`) **[факт]**. Твердження спеки M17 §3.3 про видимість відмов у консолі — **не реалізоване** (виправлено в спеці M17 цим PR).
8. **Швидкодія.** Таймінги етапів — на READY-записі (нуль — у `select_s`); три датасети ≈ 1.7–1.8 с на батч (docs 10); кожен коміт перечитує файли всіх READY-датасетів — компіляція росте з робочим простором; виміру з ≥ 10 завантаженнями немає **[факт]**. `engine.py` рівно на межі 1 000 рядків (`tests/test_architecture.py`) **[факт]**.

## 4. Workflow аналітика (один рейк, одна модель)

1. Додати датасет (файл або готовий) — система визначає структуру, рівні `@auto`, час; майнить (або, з *Лише шар*, лише зберігає точки).
2. Додати інші датасети так само; або використати вже завантажені.
3. У панелі *Крос-типовий аналіз* назвати **ціль** (чиї метрики шукаємо) і **шари** (≤ 2; умова); за потреби — «і навпаки».
4. Система пропонує рівні (найдрібніший цілі ∪ спільні зі змайненими шарами) і радіус диска; показує часове правило кожного шару (§7).
5. Прогін — ті самі етапи конвеєра; результат — датасети цілі з позначкою `+ <шар>` у її групі, лише знахідки з умовою на шар.
6. У шухляді й на мапі — вердикт нуля для кожної знахідки; на картці — відсіяні за причинами й попередження.
7. Видалити прогін (як датасет), шар (його прогони лишаються, позначаються застарілими — P1), ціль (її прогони йдуть з нею).

Режими використання даних, про які каже бриф, — три стани одного рейка: **змайнено** (звичайний датасет), **лише шар** (запис `LAYER`), **читання з фільтром** (P1, S4). Ролі не є станом датасету — вони належать прогону, тож «зміна ролі» — це інший прогін, а не редагування запису. Шар приєднується до цілі трьома способами: (A) файли контексту в одному завантаженні (`context`/`context_geo`/`context_ring`), (B) готовий набір `context_demo`, (C) збережене завантаження «лише шар» + прогін між збереженими; канон демонстрації й M18 — (C); A і B лишаються для разових завантажень і в M18 не розвиваються.

## 5. Ціль і умови

- **Ціль** — датасет, чиї метрики (лічильник, медіани, частки, часові метрики комірок) шукає майнер; **шар** — лише джерело умови `context_<шар>_band`. Крос несиметричний: `A × B` і `B × A` — два різні питання і два прогони («і навпаки»). Симетрії в інтерпретації немає: `p_context` перевіряє, чи пояснює розклад шару зсув метрики цілі, не навпаки.
- Шар може бути не змайненим (`LAYER`) або змайненим датасетом — для прогону це байдуже: читаються його точки з файлу.
- Статистична залежність ≠ причинність: словник і документи кажуть «поруч більше X — інший склад Y», не «X спричиняє Y» (docs 03, 13).

## 6. Єдине правило просторового зіставлення

1. **Базове представлення цілі** — її найдрібніший рівень (обраний `@auto` або явно). Воно ніколи не огрублюється через шар.
2. **Шар рахується зі своїх точок на сітці цілі** на роздільності цілі (сума по диску `context_ring` навколо кожної комірки цілі; комірки без подій цілі теж рахуються як сусіди). Шару не потрібен власний рівень; його рівні, якщо він змайнений, кажуть лише, де на нього вже дивились.
3. **Рівні прогону** — найдрібніший рівень цілі ∪ рівні, які має кожен змайнений шар; або рівні, які користувач обирає серед рівнів цілі. Грубші рівні завантаження — завжди регіональні (7, 5, 3, 1), тому «спільний рівень» двох завантажень — переважно регіональний (r7 ≈ 5 км²), де ефекти кварталу зникають; саме тому найдрібніший рівень цілі входить завжди.
4. **Різна деталізація джерел** вирішується п. 2 (шар завжди агрегується до комірок цілі), не огрубленням цілі.
5. **Часткове покриття** — смуга `none nearby`; шар, що дає одну смугу на рівні, вилучається з попередженням (`context_bands`).
6. **Дублювання на вкладених рівнях.** Кожен рівень — окремий датасет і окрема сім'я тестів (як у будь-якого багаторівневого завантаження); ланцюг масштабів з'єднує їх під час читання. Та сама знахідка на r9 і r7 — два інсайти; це документована властивість, а не помилка; дедуплікація між рівнями — поза межами POC.
7. **Межа:** один рівень читається з радіусом 0, 1 або 2 — параметр прогону, не хоста (спека M17 §14.6).

## 7. Єдине правило часового зіставлення

Семантику часу датасету система визначає **з його запису**, а не з назви колонки: подієвий датасет — той, що завантажений з опцією `time` (колонка прочитана, спан відомий на READY-записі `temporal.span`); статичний — без неї. Для завантаження «лише шар» колонку часу можна оголосити (P0, #254) — тоді в запису є `span`.

| Ціль | Шар | Правило | Стан |
|---|---|---|---|
| подієва (з часом) | без часу (бари, станції) | лише простір: шар — статичний контекст | є |
| подієва | подієвий (змайнений датасет або шар з оголошеним часом) | **статичне читання за весь спан шару** + попередження прогону: обидва спани і частка перекриття спану цілі; `time_rule: events` на запису контексту | P0 (#254) |
| подієва | подієвий | `align=span`: рахуються лише події шару в межах спану цілі (спан — `temporal.span` власного читання цілі, той, що покривають її ряди; не колонка файлу, як планувалось: спан уже записаний і збігається з рядами); шар без часу під `align` — цілим, із попередженням; відбиток інший лише для вирівняних прогонів | є (#256) |
| подієва | подієвий | смуга шару на кожен період цілі (вирівняні за сіткою лічильники) → наявні траєкторії інсайтів | P2 |
| будь-яка | агрегована таблиця (лічильники на локацію й період) | поза межами: шар — точки | — |
| будь-яка | об'єкти з періодами чинності | поза межами, доки колонки `valid_from/valid_to` не оголошено (P2); «поточні ліцензії» читаються як статичні й так підписуються | P2 |
| без часу | будь-який | лише простір | є |
| подієва | час шару є, але спан невідомий (не READY, не оголошено) | статично; попередження «спан не порівняно» | P0 |

Збіг простору й часу — умова **формування кандидатів**, не доказ: кандидатів судять тест медіани (з `n_eff`) і нуль перестановок. Лаги й послідовності подій — поза межами POC (окремий аналіз, не умова комірки).

## 8. Кілька датасетів: межа, комбінаторика, статистика

- **Режим POC** — спрямовані **парні** залежності: одна явна ціль, ≤ 2 шари на прогін (виміряно, спека M17 §14.6: сім'я Бонферроні ×25 з двома шарами на злочинах, контекстні когорти займають 46–49 з 50 місць валідації, п'ятий шар відкидає всі 3-кон'юнкції на ДТП). Три й більше шарів відмовляються. Ланцюжок парних прогонів (A×B, A×C, B×C) — так, окремими прогонами; одночасне багатостороннє зіставлення — поза межами. **Комбінаторика читань обмежена так само:** `where` — одна колонка й одне значення, у консолі один фільтр на читання (без «кожен тип × кожен шар × кожен радіус»); канонічний шлях демонстрації — одне читання цілі + один шар + радіус за правилом спайка; вимір #259 — 3–5 завантажень і 2–4 прогони, не повна сітка.
- **Сім'я тестів** — на прогін (датасет), як на будь-яке завантаження: `n_tests` = когорти × метрики, нуль поправлено на контекстні когорти прогону. **Глобальної поправки між прогонами немає** — так само, як між незалежними завантаженнями сьогодні; записано як обмеження, не як дефект.
- **Ризики й що їх покриває:** множинне тестування — Бонферроні в межах прогону; спільна щільність — нуль у батьках; мала потужність і малі комірки — `MIN_CELL_POINTS`, `MIN_SUPPORT_ROWS`, частки NaN у рідких комірках; повторний облік на вкладених рівнях — §6 п. 6 (документовано); вибірковий показ лише сильних зв'язків — відмови видимі за причинами (P0, #253), повний список — маршрут (P1, #258); залежність від набору умов — скоупи з кількома умовами несуть усі їх у тексті; тест медіани на малих частках — властивість ядра (спека M17 §13 п. 6), не M18.
- **Вартість:** секунди нуля ростуть з контекстними когортами (5 с з двома шарами на злочинах з git); компіляція знімка росте з робочим простором (кожен коміт перечитує всі READY-датасети) — вимір на 3–5 завантаженнях і 2–4 прогонах — #259; інкрементальний перерахунок лише залежних частин графа вже є моделлю коміту (один батч — один коміт).

## 11. Архітектурний план і контракти (мінімальні зміни)

Новий конвеєр не з'являється: прогін — це `load_dataset` з шарами → той самий майнер → той самий коміт. Зміни локальні; політика живе в `insight_graph_service/core/uploads.py`, `engine.py` лише викликає (він на межі бюджету рядків).

**Контракти.**

- *Місце в `engine.py`* (#254): `SOURCE_MAX_CHARS` і `resolve_dataset_metadata` переносяться в `uploads.py` (єдині виклики — в engine); невживані імпорти прибираються; поведінка байт у байт.
- *Час P0* (#254): `store_layer(time, tz)` читає колонку раз і пише `span` на запис `LAYER`; `cross_runs` пише на кожен запис контексту `time_rule: static|events` (+ `time`, `tz`, `span`) і повертає попередження → `submit(warnings=())` → `record["warnings"]`; частка перекриття = перекриття / спан цілі (спани — з `temporal.span` READY-запису або `span` запису шару, без нової логіки спанів); Відбиток не змінюється — правило P0 лише анотує запис; перша зміна відбитка часом — `align=span` (#256).
- *Вирівнювання* (#256, зроблено): `CrossTypeIn.align: "span" | None`; `window` на записі контексту; `read_context(…, window=(time, tz, lo, hi))` фільтрує після кешу (кеш тримає час, тож невідфільтроване не перевикористовується); частина шару у відбитку `<шар>:<sha12>:<локатор>[:<time>@<lo>..<hi>]`; `uploads.context_files` — одне місце, де запис стає входом `load_dataset`. `ContextSource.times` не додано (YAGNI: потрібне лише смугам на період, P2).
- *Поділ* (#257): `where="<колонка>=<значення>"` (одна колонка, одне значення; `!=` і множини — згодом тим самим рядком). **Відфільтроване читання — власний `upload_id`, не копія файлу:** `upload_id(path, where)` хешує байти ‖ `where=`, `source_path` — єдиний збережений файл, фільтр застосовується на льоту після `read_file`; усі ключовані `upload_id` місця лишаються правильними без змін. У відбитку `where=` лише коли задано (golden незмінний); ключ профілю точок `(digest, locator, where)` — обов'язково. **Один шлях фільтра:** `where` розбирається раз на межі (`parse_where`) і застосовується одним `filter_rows` після `read_file` — для читання цілі (`where` завантаження) і для шару (`CrossTypeIn.layer_where: {upload_id: spec}`, лише для шарів, збережених цілком; назва `<stem>_<значення>`) однаково; `save_context` не фільтрує; `where` + `layer` на одному завантаженні — відмова (стале завантаження «лише шар» — цілий файл, фільтр шару — на прогоні); ціль і шар з одним `upload_id` — 400, однакові байти під різними `upload_id` (інший `where`) — дозволено; шар — власний файл цілі — посилання, не копія. Консоль: одне текстове поле або вибір значення зі списку, який повертає відмова сервера; рекомендувача колонок немає. Константна колонка відкидається. Придатність (без прив'язки до даних): нечислова, не точкова й не часова колонка з 2–40 рівнями; значення цілі — ≥ `MIN_ROWS × MIN_CELL_POINTS` рядків, значення шару — ≥ `MIN_ROWS`; відмова сервера перелічує значення з лічильниками. Чи відновлює поділ частотні гіпотези літератури — вимір (спайк `@10` з радіусом 0 після #257; замикання все ще може переказати `points` через `lisa_points` на гарячих точках), не обіцянка #255.
  *Зроблено (#257):* як вище, з двома спрощеннями: поріг значення — «хоч один рядок» (замалий результат відмовляє, як будь-який замалий датасет, `MIN_ROWS`; окремі пороги для цілі й шару не додано); файл не копіюється лише для читань з `where` (`uploads.stored_copy` повторно бере збережений файл тих самих байтів), звичайне завантаження зберігає свій файл, як досі. Тести — `tests/test_crosstype_readings.py` (3).
- *Застарілість і походження* (#258, зроблено простіше за план): `stale: {layers, reason: deleted|superseded}` і `layer_of: n` **не пишуться**, а читаються з реєстру на кожен запит (`uploads.cross_state` — чиста функція реєстру; `GET /api/batches` додає їх до записів): відкочене видалення не лишає позначки за побудовою, ідемпотентність — без зусиль, `engine.py` не змінено, `BATCH_DIGEST_FIELDS` без змін; `at` відкинуто (за реєстром не відомий, потреби немає). Dataset-вузол несе `cross` і `cross_layers` — шухляда (*Походження*) і рядок `DATASETS` промпту називають прогін із шаром; `GET /api/datasets/{id}/rejections` — посилання з картки (рідний перегляд JSON браузера: розгортання на картці гинуло б при оновленні рейки).
- *Видимість* (#253): дані вже в payload-ах; консоль показує `p_context · m` і диск у шухляді й на картці мапи, `metrics.pruned` за причинами й `warnings` на картці; слова диска — одна функція від радіуса (для `wording.py` і чипа шухляди), радіус — із запису батча (`context_ring`, уже збережений; англійський `glossary` шару вже правильний за радіусом); **без нового поля `SpatialProvenance`** — дайджест і `verify` не змінюються заради рядка показу; маршруту відмов (#258) не чекає — причини з `metrics.pruned`.

Правила оновлення графа: новий датасет — окремий коміт (є); новий прогін — окремий коміт (є); зміна ролі — інший прогін (стану немає); зміна поділу — інше читання, інший `upload_id` (P1); видалення датасету/прогону — як сьогодні (правило сироти); видалення шару — прогони цілі, позначені застарілими (P1); заміна цілі — її прогони видалено разом із нею (є); зміна контексту часу/простору — інший прогін (інший відбиток).

## 12. Chicago Crimes + Bars — обов'язковий демонстраційний сценарій

**Послідовність аналітика (консоль):** (1) *Або готовий датасет* → `chicago_crimes` → *Аналізувати* → READY `@9` (з типовими опціями маніфесту); (2) *Лише шар* + `chicago_bars` → картка «chicago_bars.csv · шар · 3 037 точок» (#252); (3) *Крос-типовий аналіз*: ціль — злочини, шар — бари, рівень r9 (попередньо позначено), радіус — типовий; *Порахувати* → картки «chicago_crimes.csv · H3 r9 · + chicago_bars» у групі злочинів; (4) у шухляді кожної крос-типової знахідки — вердикт нуля; на картці — відсіяні за причинами (#253); (5) те саме зі станціями 'L' — друга пара. **Часова особливість.** Злочини — події з часом; бари — поточні ліцензії без періодів чинності → шар статичний (§7, перший рядок), часова мітка цілі не накладає обмежень на шар. Періоди чинності в джерелі є, але не постачаються, і їх використання — P2 (§10).

**Спайк #251 — записано до прогону.** Прогони через `Engine.cross` (шлях демонстрації) на злочинах 2025 з git (з `district`): × бари і × станції 'L', при `@9` з радіусом 1 і 0, `@10` з радіусом 0 (явний рівень). Очікування, за спекою M17 §14 **[висновок]**: `@9`, радіус 1, бари — нуль допускає 0 (тест медіани 10–20 знахідок складу, усі `context_confounded`); станції 'L' — 0–1; радіус 0 і `@10` — **[невідомо]**: ефекти в самій комірці можуть з'явитись або ні. **Правило рішення:** типові налаштування демонстрації не змінюються; якщо при радіусі 0 нуль допускає ≥ 1 знахідку для барів, а при радіусі 1 — жодної, інструкція радить «лише саму комірку» для шарів із локальним зв'язком і пояснює чому; якщо нуль не допускає нічого за жодних налаштувань — демонстрація показує відмови з причинами як результат, а станції 'L' — як другу пару. Пороги `MAX_P_ADJUSTED`, `MIN_EFFECT_Z`, `CONTEXT_PERMUTATIONS` не чіпаються. Числа — у §12a після прогону.

**Критерії демонстрації:** відтворюється браузерним тестом від порожнього простору (#255) і людиною за інструкцією docs 10 §10.2; дані з git з документованим походженням (`SOURCES.md`); результати в графі (картки, шухляда, мапа); повторний запуск — `SKIPPED` за відбитком; вердикт — як дають дані: **приймання не вимагає допущених інсайтів** — шлях доходить до карток прогону; картка прогону — лічильники `context_confounded`/`outside_cross_type` (і для прогону, що не допустив нічого: когорта, яку ворота відкинули, інсайтом не стає, тож шухляди в неї немає); шухляда кожної допущеної знахідки — *нуль шару* `p_context · m`; кількість допущених — «як виміряно в #251», включно з нулем.
