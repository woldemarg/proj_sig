# 2. Discovery — from a table to validated subgroups

> **In one paragraph.** Ingestion validates the uploaded file, optionally turns number-coded columns into categories and numeric columns into quantile bands, and gives the dataset a content-addressed id. The vendored automatic-EDA engine then searches conjunctions of two and three `attribute = value` selectors in two passes: a cheap screen for robust median shifts and correlation changes, and an expensive bootstrap validation of the best 50. Between the passes the adapter merges selectors that cover identical rows and prunes near-duplicate cohorts, so the bootstrap is spent only on distinct subgroups. The adapter also adds what the EDA does not produce — the direction of each shift, a significance test, provenance — and hands typed candidates to [3. Insights](03_insights.md).

## 2.1 Ingestion

`load_dataset(path, config, filename=, bins=, categories=, geo=)` (`config` a `MinerConfig`) turns a file into a `LoadedDataset(frame, dataset_id, filename, bins, categories, derived_columns, warnings, geo, spatial)`.

| Input | Form | Source |
|---|---|---|
| file | `.csv`, `.tsv`, `.txt`, `.parquet` | `POST /api/upload` (the console's upload; saved under `WORKSPACE_DIR/uploads/`), `POST /api/demo` / `POST /api/demo/geo`, or a path given to `Engine.ingest_file` (the measurement scripts, the tests) |
| `bins` | `"col:q,col2:q"` (`col` alone means 4 quantiles); `""` = none; `None` = workspace default `BIN_COLUMNS` | UI *Розбити числа на смуги* = the form field `bins` of `POST /api/upload` |
| `categories` | `"col,col2"`; `""` = none; `None` = workspace default `CATEGORICAL_COLUMNS` | UI *Вважати категоріями* = the form field `categories` |
| `geo` | `auto`, `<column>` or `<lat>,<lon>`, optionally `@<resolution>` (an upload may list several, `@8,5`, or read them from the points, `@auto`, and add `table`: one dataset per level, [2.9](#29-spatial-datasets-the-geo-option)); `None` = a plain table | UI *Spatial analysis (H3 cells)* = the form field `geo`; rows become H3 cells first ([2.9](#29-spatial-datasets-the-geo-option)) |
| `indicators` | `"metric:indicator[:unit],…"` — what a metric measures and in which unit (each field one line, at most 60 characters, no `:` or `,`; each metric once); `""` = none | UI *Що вимірюють метрики* = the form field `indicators`. Metadata like the next row: on the batch record, outside the dataset id, replaced as a whole by `PATCH /api/datasets/{id}` (which refuses a metric the dataset does not have); at upload an unknown metric is dropped with a warning that lists the dataset's metrics, since they are known only after profiling. The names are those of the analysed table: for a geo dataset the cell metrics (`points`, `<column>_median`, `<column>_active_days`, `<column>_late_share`, `share_<column>_<level>`; [2.9](#29-spatial-datasets-the-geo-option)), not the source columns. A malformed spec is `invalid_options` before the file is stored |
| `glossary` | JSON `{"column": "meaning", "column=value": "phrase"}` (each value at most 120 characters); `""` = none | UI *Що означають колонки*. Metadata like `indicators`: on the batch record, outside the dataset id. A column is named as in the file: it counts when the dataset holds it as itself, as its band (`<column>_band`) or as a geo cell's derivation (`<column>_median`, `_mode`, `_late_share`, `_active_days`, `share_<column>_<level>`; `wording.source_column`). One it does not hold is dropped with a warning at upload (one glossary serves every level of a `geo` + `table` upload) and refused by `PATCH`; a `column=value` whose value no row holds is a warning, kept. Malformed JSON is `invalid_options` before the file is stored |
| `metadata` | a metadata document: UTF-8 text of at most 64 KB. The lines before `Columns:` describe the dataset as `Key: value` (`Type`, `Display name`, `Description`); then one block per column, apart by blank lines: its name on an unindented line, its fields indented as `Key: value` (`Type`, `Display name`, `Description`, `Assistant context`, `Title (uk)`, `Title (en)`; any other key is kept as it is). A field sits at the indentation of its block's first field (or, before `Columns:`, of the header's); any other line — a deeper one, though it holds a colon, or one without a key — continues the previous value. A BOM and CRLF are read; `""` = none | UI *Документ метаданих* (a file). Parsed onto the batch record (`uploads.parse_metadata_doc`; a key in snake case, `Title (uk)` → `title_uk`). A document without `Columns:` or a column, above 64 KB or not UTF-8 is `invalid_options` before the file is stored |
| `source`, `reliability` | free text on one line (whitespace collapsed, at most 120 characters); an Admiralty source-reliability code `A`–`F` (default `F`, cannot be judged); `""` = undeclared | UI *Джерело* and *Надійність джерела* = the form fields of the same names. Not analysis options: they are stored on the batch record, never enter the dataset id, and `PATCH /api/datasets/{id}` changes them later ([6.2](06_graph_and_storage.md#62-the-graph-schema)) — a re-upload of the same file is `SKIPPED` and changes nothing (its warning names the `PATCH`); an invalid value is refused with `invalid_options` before the file is stored |
| `supersedes` | a dataset id or an upload id (`up-…`) of the version this upload replaces; `""` = none | Metadata like `source`: on every level's batch record, outside the dataset id. Once the new version is READY the old one is deleted ([6.8](06_graph_and_storage.md#68-deleting-a-dataset)); refused with `invalid_options` for an id no READY dataset or upload has, and for the very file it would replace. Set later by `PATCH /api/datasets/{id}` (API only) |

An empty or missing upload field means "workspace default" (`None`); `POST /api/demo` (the UI's *Демо: таблиця*) sends an explicit `""` for both options, `POST /api/demo/geo` (*Демо: мапа*) its band and geo option; `Engine.submit` takes the options (`None` unless one is passed; `bins=""` is an explicit "none"), and `Engine.ingest_file(path)` submits with the workspace defaults.

**One declared glossary.** What the uploader declares about the columns is folded at commit into one glossary on the Dataset node, `user_glossary` (`uploads.declared_glossary`): a documented column's `Title (uk)`, else its `Display name` (a name: clipped at 120 characters, as a glossary value); over it, for a metric the document does not name, its indicator `<indicator> (<unit>)`; over everything the explicit `glossary`. A column reads the same whichever way it was declared: every reading ([8.5](08_interface.md#85-text-shown-to-people)), the prompt's `PLAIN LANGUAGE` and `DATASET CONTEXT` ([7.4](07_question_answering.md#74-the-evidence-object)) and the dataset card use it. The parsed document rides on the node as `metadata_doc`; an empty field is not written, so a dataset that declares nothing compiles as before. Both are signed with the record ([6.7](06_graph_and_storage.md#67-configuration-and-guarantees)) and dropped from a record that fails its digest. The derived English `profile.geo.glossary` of a geo dataset stays the map's ([8.7](08_interface.md#87-the-map) suggestions) and the prompt's base under the declared one; on a geo level a declared source column reads onto every cell column derived from it (`share_channel_phone` reads the declared `channel`, `wording.column_words`) and a declared `column=value` onto the cell's mode column (`ocean_proximity=INLAND` reads `ocean_proximity_mode=INLAND`), and any column's quantile band reads as the column, in the readings and in the prompt alike.

Before a batch exists, `Engine.upload` refuses a file above `MAX_UPLOAD_MB` (200): it deletes the upload and raises `file_too_large`, which the API answers with HTTP 413. Steps, in order:

1. **File.** A missing file → `unsupported_file`.
2. **Options.** The band and category specs are parsed before the file is read; a malformed spec → `invalid_options`.
3. **Type and parse.** Unknown extensions → `unsupported_file`. CSV and `.txt` take the delimiter `csv.Sniffer` reads from the first line, as pandas' Python parser sniffs it, and are parsed by the C parser into the frame that parser gave — one type per column from all its rows (`low_memory=False`) — in a quarter of its time (300,000 rows: 0.15 s against 0.61 s). A leading BOM (Excel's «CSV UTF-8») is not part of the first column's name, and the delimiter is sniffed without it. TSV takes a tab, read in chunks as the C parser does by default; when a chunk types a column otherwise than the rest — numeric-looking codes followed by text leave values of two types in it, and an integer chunk beside a float or an unsigned one turns integers past 2^53 into rounded floats, without pandas' mixed-type warning — the file is read whole, one type per column. Any other TSV is parsed once (300,000 rows with six text columns: 0.37 s, where a second, whole read cost another 0.34 s). Parquet takes `read_parquet` (without pyarrow installed: `unreadable_file`). The dataset id hashes the file's bytes as a stream. For a file that an older reading turned into another table — a CSV with a BOM, which kept the BOM in the first name, and a TSV read whole — the hash also takes `ingestion.READING_FIX`. Such a file gets a dataset id of its own: a dataset made from it before checks as `source_changed`, and uploading it again is no duplicate. Every other file keeps the id its bytes always gave. Of the 27 shipped and synthetic files (the California demo, the retail demo, the delivery sets of 30,000, 300,000 and 1,000,000 points, the geo benchmark's uploads, three of them also as TSV), none is read otherwise. The levels of one upload share one parse (`read_file(shared=True)`): the `@auto` choice, each level and each dataset id; the engine drops it once no batch waits and when an upload is refused (`forget_tables`). Any other read — a re-check of the source among them — parses the file as it is now. Parser errors → `unreadable_file`. pandas' default NA parsing applies: a literal `NA` becomes missing, which is why the synthetic region is called `US`, not `NA`.
4. **Shape.** Fewer than 2 columns or fewer than `MIN_ROWS` (50) rows → `invalid_schema`.
5. **Categories, then bands.** A *categorical override* casts a column to text (`Int64` first when it holds integral floats, so `1.0` becomes `"1"`; NaN becomes `missing`): this is how integer-coded dimensions such as `Store` or `Holiday_Flag` become scope columns instead of metrics or identifiers. A *band* derives `<col>_band` with values `q1 … qk` (quantile bins, duplicate edges dropped) plus `missing`, and **drops the source column**, so the band acts as a dimension and can never become a tautological target (`median_income` shifting inside `median_income_band = q4`). Workspace defaults (`None`) are applied leniently — columns the dataset lacks are skipped with one warning — while an explicit option is strict: an unknown column → `invalid_options`. A band on a non-numeric column is `invalid_options` in both modes; since categories are applied first, that includes a column named in both options (it is already text when the band is made). Because NaN becomes the level `missing` (not a null), `x_band = missing` can be a selector like any other value.
6. **Targets.** No numeric column → `no_numeric_targets`. All-null columns produce a warning.

The dataset id is a pure function of the bytes and the applied options:

```text
dataset_id = "ds-" + sha256( file bytes ‖ repr(sorted(bins.items())) [‖ repr(sorted(categories)) when any apply]
                             [‖ "geo=<locator>@<res>" with the geo option] [‖ "left_out=[…]" for a table level's point columns] )[:12]
```

Identical content with identical options always gets the same id; a second upload of it is `SKIPPED` ([9.1](09_operations.md#91-the-batch-lifecycle)). The frame keeps the file's row order, so EDA row positions are file rows. The file itself is not copied: an upload stays under `uploads/`, and the batch record's `source_path` names it (provenance; [6.3](06_graph_and_storage.md#63-the-workspace-on-disk)). Semantic typing (identifiers, categoricals, redundant columns) is not done here: it is EDA step 1.

> **Running example.** `retail_synthetic.csv`: 5,000 rows × 11 columns, no bands, no overrides → `ds-6e53eb7fb0f9`. On real data the options matter: `housing.csv` needs `bins=median_income:4,housing_median_age:4` (only one native categorical).

## 2.2 The EDA engine in five steps

The adapter (`discovery.run_discovery(df, config, on_stage=None)`; `on_stage("DISCOVERING")` is called once profiling and the search space are done, which moves the batch from PROFILING to DISCOVERING) calls the vendored engine step by step, in the order of the EDA's own workflow, and converts its DataFrames into typed objects; downstream of discovery the pipeline reads only typed candidates, the profile, the rejections and the covers. Two process-wide side effects come with the engine: importing it silences `RuntimeWarning`, and the adapter reseeds NumPy's global RNG before the bootstrap. Notation for this chapter:

| Symbol | Meaning |
|---|---|
| `N` | rows of the profiled table |
| `m` | metric (numeric) columns kept by profiling |
| `S`, `n = |S|`, `p = n / N` | a subgroup (the rows covered by a conjunction of selectors), its size and share |
| `med`, `MAD` | median; median absolute deviation around the median |
| `z_k(S)` | the robust shift of metric `k` inside `S` |
| `C`, `C_S` | rank correlation matrix of the metrics over all rows / over `S`: the ranks are taken once over the whole table (`step1`), so `C` is Spearman's and `C_S` the Pearson correlation of those global ranks inside `S` — one robust association for both phenomena, where the shift is median over MAD and one tail value cannot carry a correlation change |

### Step 1 — profile the table (`step1_profile_data`)
1. **Identifiers** are dropped: a column with `nunique == count(non-null)` whose dtype is not float (continuous measures are all-unique by nature, so floats are never identifiers).
2. **Typing**: numerics are numpy numeric dtypes; categoricals are object / category / bool / string, cast to `str` — a null categorical value becomes the string `nan`, which counts in the checks below and can be named as a confounder level but never becomes a selector. Columns of any other dtype (dates, for example) are dropped.
3. **Constant categoricals** (`nunique ≤ 1`) are dropped before any pair rule — a single-valued column is trivially "a function of" every other column.
4. **Nested columns**: for a pair of categoricals with `|distinct (a, b) pairs| ≤ 1.10 · max(nunique)`, the finer column is dropped (on a tie, the later one), but only when the coarser one is informative (its top level holds < 95 % of rows).
5. **Numerics**: zero-variance columns are dropped; then a column is dropped when any earlier column has `|corr| > 0.95` with it (also an earlier column that was itself dropped). `C` is computed over the kept metrics (`NaN → 0`).

### Step 2 — choose the dimensions (`step2_evaluate_macro_groupings`)
For each categorical `g` with `nunique(g) ≤ √N` and each metric `y`, over the rows where both are present (`k ≥ 2` groups, `n > k`):

```text
SS_between = Σ_groups n_i (ȳ_i − ȳ)²      SS_total = Σ (y − ȳ)²      MS_within = (SS_total − SS_between) / (n − k)
power(g, y) = ε² = max(SS_between − (k − 1) · MS_within, 0) / SS_total
```

ε² is η² = SS_between / SS_total with its chance expectation `(k − 1)/(n − 1)` removed, so a 45-level column does not outrank a 3-level one by chance. `power(g)` is the mean over metrics; columns above the median power are kept (at most 6), and if fewer than `MIN_SEARCH_DIMENSIONS` (3) survive, the strongest remaining eligible ones are back-filled so that 2- and 3-conjunctions exist. A column with more than `√N` levels is never eligible, not even for the back-fill.

### Step 3 — build the search space (`step3_generate_search_space`)
Per selected dimension, levels are ordered by share and kept up to and including the one that crosses 95 % cumulative mass — only the long tail is dropped, so a 60/40 column keeps both levels; `nan` / `<NA>` / `None` levels are skipped. Candidates are all conjunctions of 2 selectors on distinct attributes, plus the 3-conjunctions when the total stays within `COMPUTE_BUDGET` (5000). When even the 2-conjunctions exceed the budget, the pairs with the largest expected support `Π f_v` (product of level shares) are kept. Single selectors are never candidates: single-attribute effects are what step 2 measures.

### Step 4 — pass-1 screening (`step4_evaluate_micro_slices`)
A subgroup is screened when `n ≥ n_min = max(5m, ⌊0.005 N⌋)` and `n ≠ N`.

**Robust scale and shift.**

```text
MAD(y) = med(|y − med(y)|);   if MAD = 0:   MAD := (0.6745 / 0.7979) · mean(|y − med(y)|)
|z_k(S)| = min( 0.6745 · |med_S(y_k) − med(y_k)| / (MAD_k + 1e-6),  ROBUST_Z_CAP = 10 )
```

`0.6745 · Δ / MAD = Δ / σ̂` with `σ̂ = MAD / 0.6745`: the shift is measured in robust standard deviations ("sd" everywhere in the UI and the prompt). The MAD fallback is the normal-consistent mean absolute deviation; without it a metric with more than half of its values tied (zero-inflated counts) made every subgroup look infinitely shifted. The cap keeps a degenerate scale from dominating the ranking. The scale `MAD_k` is the global one, so shifts are comparable across subgroups.

**Scores.**

```text
SD(S)      = sum of the three largest |z_k(S)|                                   (top_shifts)
Δ          = C − C_S, with Δ_ij := 0 where C_S,ij is undefined (metric constant in S); only when n ≥ 3m and m ≥ 2
EMM_eda(S) = ‖Δ‖_F / sqrt(m(m − 1)) · sqrt( max(0, n − n_min) / (N − n_min) )   (RMS per pair · reliability shrinkage)
vol(S)     = √p · (1 − p)                                                        (maximal at p = 1/3: 0.3849)
```

`SD` rewards median shifts, `EMM` rewards a changed correlation structure (exceptional model mining), `vol` rewards moderate, actionable subgroups over near-majorities. The shrinkage pulls correlations estimated from few rows towards "no change"; an undefined local correlation is no evidence of change, not a change to 0. `m` counts the metrics the scope may explain: on a geo dataset a metric a condition is computed from is in no pair ([2.9](#29-spatial-datasets-the-geo-option)).

### Step 4b — pass-2 validation (`step4b_deep_validation`)
**Bootstrap stability.** For `B = 20` resamples of `S` (n of n, with replacement; the adapter seeds the global RNG with `EDA_RANDOM_SEED`):

```text
b_r = Σ_{k ∈ top_shifts} |z_k(S_r)|        CV = std(b) / (mean(b) + 1e-6)
final_sd = SD(S) · (1 − min(CV, 0.9))      stability = final_sd / SD(S) = 1 − min(CV, 0.9) ∈ [0.1, 1]   (0 if SD(S) = 0)
```

The adapter seeds the RNG once before the whole step, so a cohort's resamples depend on its position in the validation order; the result is reproducible for the same data and configuration.

**Confounders** (categoricals outside the subgroup's own scope). With `q_S`, `q` the level distributions inside `S` and overall, a column is a driver when `jensenshannon(q_S, q) > 0.15` (scipy's JS *distance*, natural log) **and** the chi-square test of independence (rows of `S` vs the rest) has `p < 0.01 / #categoricals`. The driver is named by the level whose share grew most. The significance gate matters: the JS distance of an empirical distribution is inflated by sampling noise in small subgroups. **Hidden shifts**: a metric outside the top three with `|z| > 1.5` is reported, signed. At most three drivers per subgroup — categorical drivers come first, so the cut drops hidden shifts first — as strings such as `[payment] heavily skewed to 'cash' (JS: 0.20)` or `[discount] hidden shift (+1.8 robust sigma)`.

> **Running example.** Profiling keeps the numerics `discount, margin, delivery_days, return_rate` and the categoricals `region, category, channel, payment, weekday, store_size`, and drops `order_id` as an identifier. Step 2 keeps `region, category, channel`; the planted noise columns `payment, weekday, store_size` fall below the median power. The search space has 88 conjunctions; 84 pass the size screen (four rare `partner` slices do not); the top 50 are validated. `category=='phones' AND region=='US'` covers 438 rows, its top shifts are discount and margin, its bootstrap stability is 0.976, and it has no confounders (the demo dimensions are drawn independently).

The vendored engine differs from upstream in a set of local, commented numerical repairs — the MAD fallback and cap, constant categoricals dropped before the nesting rule (which needs an informative coarser column), ε² instead of η², the 95 %-mass rule, the over-budget truncation, NaN-aware EMM on rank correlations (the ranks taken once, pass 1 reading subgroups from one array instead of a frame copy each), the full-size bootstrap, confounders gated by a chi-square test and named by the level with the largest share gain, signed hidden shifts — each listed with its reason in [`subgroup_miner/vendor/PROVENANCE.md`](../subgroup_miner/vendor/PROVENANCE.md).

## 2.3 Deduplication before validation

The bootstrap of step 4b is the expensive stage and `VALIDATION_BUDGET` (50) slots are scarce. Two selectors that cover exactly the same rows are one subgroup described twice, and two cohorts that overlap almost completely with the same effect are one finding. `run_discovery` therefore removes redundancy **between pass 1 and the ranking into step 4b**:

1. **Closure** (`merge_identical_extents`). Pass-1 selectors are grouped by extent (the set of covered rows). Each group becomes one cohort described by its **closed intent**

   ```text
   int(ext(S)) = { (a, v) : a is a profiled categorical, every covered row has a = v, v is not null-like }
   ```

   — the Galois closure of formal concept analysis: every condition that holds on all of the cohort's rows, including conditions the selector did not state (an implied column). `expression` keeps the member selector with the most conditions; the other selectors become `aliases` and `Rejection(…, "cover_equivalent")`.
2. **Ranking.** `temp_index = clip₊(zscore(SD)) + clip₊(zscore(EMM_eda)) + clip₊(zscore(vol))` over the distinct cohorts (scipy's population z-score, `NaN → 0`) — the EDA workflow's own ranking.
3. **Near duplicates** (`prune_near_duplicates`), greedy in `temp_index` order: a cohort is absorbed as an alias of a higher-ranked kept cohort with the same primary metric (pass-1 top shift), the same sign of `med_S(y) − med(y)` and

   ```text
   J(A, B) = |A ∩ B| / |A ∪ B| ≥ REDUNDANCY_JACCARD (0.88)        (boolean row masks)
   ```

   → `Rejection(…, "near_duplicate")`.
4. **Validation.** The first `VALIDATION_BUDGET` survivors go to step 4b, with the closed intent's attributes passed as their scope, so an implied attribute is never reported as a confounder of its own cohort.

The Bonferroni family is `n_tests = distinct cohorts × m`: identical extents are one test. Because conditions are closed intents, the lattice of [6.1](06_graph_and_storage.md#61-the-structural-plane) is the Hasse diagram of a concept lattice: a strictly smaller extent always has a strictly larger intent.

## 2.4 What the adapter adds

| Addition | Definition | Why |
|---|---|---|
| conditions | the closed intent, sorted `(attribute, str(value))` | a typed scope for the lattice; identical cohorts get identical pattern ids |
| signed shift | `z_k(S) = sign(med_S(y_k) − med(y_k)) · |z_k(S)|` (a zero difference counts as +) | the EDA keeps magnitudes only; direction drives CONTRASTS, the phenomenon vector and the answer |
| EMM per pair | `emm_score = EMM_eda`: the RMS correlation change per pair of the metrics the scope may explain (`correlation_change` in the vendored step 4; re-scored at closure when the closed intent restates more metrics), so `temp_index`, step 4b and the insight all see the per-pair value | the Frobenius norm grows with the number of off-diagonal entries; per pair it is an RMS correlation change in `[0, 2]`, so `MIN_EMM_SCORE` means the same on every dataset |
| covariance pair | `argmax_{i<j} |C_S,ij − C_ij|` over pairs defined in `S` (needs `n ≥ 3m`; `{}` if none) → `{pair, local_corr, global_corr, delta}` | says *which* relation drives the EMM score |
| pair shifts | `z_k(S)` for pair metrics missing from the top three (`Shift.source = "covariance_pair"`) | lets a correlation-change insight be targeted on one of its metrics |
| significance | two-sided asymptotic median test on the primary metric, `se = 1.2533 · 1.4826 · MAD(y_S) / √n` with the subgroup MAD computed like the EDA's (zero-MAD fallback included); if that is 0, the global MAD; if that is 0 too, `se = sd(y_S) / √n`. `z = (med_S − med) / se`, `p = 2 · Φ̄(|z|)` (`p = 1` for `n < 2` or a zero or non-finite `se`); `p_adjusted = min(1, p · n_tests)` | the EDA has no p-values; selection and weight need one. Bonferroni over overlapping cohorts is conservative, never anti-conservative |
| stability | `final_sd / sd_raw = 1 − min(CV, 0.9)` | recovers the bootstrap factor that step 4b folds into `final_sd` |
| determinism | `np.random.seed(EDA_RANDOM_SEED)` before step 4b | `DataFrame.sample` uses the global RNG; same data and config → identical insights |
| provenance | dataset, file, batch, engine path (`subgroup_miner/vendor/eda/main_upd.py`), steps, exact selector, size of the testing family; the graph service adds `rows_ref` (`datasets/<ds>/covers.npz#<pattern id>`) to the journal record | traceability |

## 2.5 Contracts

* `run_discovery(df, config, on_stage=None, spatial=None) → DiscoveryResult(profile, candidates, validated, data, n_tests, pass1_subgroups, rejections, spatial)`: `candidates` are the distinct cohorts, `validated` the ones step 4b returned, `rejections` the `cover_equivalent` / `near_duplicate` merges (and `tautological` ones of a geo dataset, added by `build_insights`); `spatial` (a `SpatialContext`) switches on [2.9](#29-spatial-datasets-the-geo-option).
* `Candidate(expression, conditions, row_indices, row_count, volume_utility, top_shifts[(metric, |z|)], sd_aggregate_score, emm_stabilized_score (per pair), temp_index, validated, final_sd_score, drivers, aliases)`.
* `build_insights(result, config, dataset_id=, batch_id=, filename=) → list[Insight]` — unfiltered, weight unset ([3.1](03_insights.md#31-the-insight-record)); the primary target is the largest shift.
* `covers_of(result) → {expression: row positions}` for every distinct cohort; `Engine.process` persists the covers of the kept insights as `covers.npz` (`Workspace.save_covers`), keyed by pattern id, and points each journal record's `provenance.rows_ref` at them (`Workspace.covers_ref`).

## 2.6 Configuration

| Parameter | Default | Effect |
|---|---|---|
| `MIN_ROWS`, `MAX_UPLOAD_MB` | 50, 200 | ingestion limits (`MAX_UPLOAD_MB` is the graph service's upload limit, a `Settings` field) |

## 2.7 Failure modes and guarantees

| Code | Raised by | Meaning |
|---|---|---|
| `file_too_large` | `PipelineError` (`Engine.upload`) | an upload above `MAX_UPLOAD_MB`; refused with HTTP 413 before a batch is registered |
| `unsupported_file`, `unreadable_file`, `invalid_options`, `invalid_schema`, `no_numeric_targets` | `IngestionError` | missing file or unsupported type, parse error, bad options, too few rows or columns, no numeric column |
| `no_numeric_targets`, `invalid_schema`, `no_candidates` | `DiscoveryError` | profiling left no metric; no categorical dimension (the message suggests `BIN_COLUMNS`); empty search space or nothing passed pass 1 |
| `internal_error` | `DiscoveryError` | a closed intent that does not contain its own selector (an invariant check that should never fire) |

Guarantees (`tests/test_discovery_contract.py`; on the demo unless a toy frame is named):
* `0 < len(candidates) ≤ search space size`, `0 < len(validated) ≤ VALIDATION_BUDGET`, `n_tests = len(candidates) · m`; by construction `len(candidates) ≤ pass1_subgroups`.
* On a toy frame with an implied column: `pass1_subgroups − len(candidates)` equals the `cover_equivalent` rejections, the merged cohort carries the implied condition and no driver for it, and the validated cohorts have pairwise distinct extents; near duplicates are pruned in rank order (a second toy case).
* Galois antitone: among validated cohorts, a strictly smaller extent has a strictly larger intent.
* Same data and config → identical insights; `Insight.support == len(covers[expression])`.
* The planted mechanisms of the demo are recovered with the right signs (the test asserts five of the six; the sixth, delay → returns, is recovered on the demo — APAC∧online and US∧laptops∧retail — and guarded by the benchmark regression of [10.3](10_verification.md#103-hypothesis-benchmark)).

## 2.9 Spatial datasets (the geo option)

An upload with the `geo` option (form field `geo` of `POST /api/upload`, `Engine.submit(geo=)`, `load_dataset(geo=)`) holds **points**, one per row. Ingestion turns them into a table with **one row per occupied H3 cell** (`subgroup_miner/spatial.py`, `build_cells`) before bands and categories apply; discovery then mines cells exactly as it mines any table. A place many points share is indexed once (`distinct_points`), there and in `select_levels`. Without the option nothing below runs and a dataset is processed — and identified — as before.

**The option.** `auto`, `<column>` (GeoJSON `Point` or WKT `POINT (x y)` text) or `<lat>,<lon>` (numeric, by position; two columns named the other way round, such as `longitude,latitude`, are read by their names, since their values lie in range either way), each optionally followed by `@<resolution>` (0–15; default `GEO_RESOLUTION` 7). `auto` takes the first text column whose first 200 non-null values parse as points for at least 95 %, otherwise the numeric pair whose names contain a `lat`/`latitude` and a `lon`/`lng`/`long`/`longitude` token. A spec that cannot be applied is `invalid_options`; rows without a valid point are ignored with a warning. The applied option enters the dataset id (`… ‖ "geo=<locator>@<resolution>"`).

**Levels of one upload.** `POST /api/upload` (`Engine.upload`) also takes `geo=<locator>@<r1>,<r2>,…` and the form flag `table`: the file is stored once and each level becomes an ordinary dataset with its own batch, queued in turn on the worker thread — one per resolution, finest first, then, with `table=true`, the file as a plain table (`table` needs `geo`). Each geo level's dataset id is that of a separate upload with that level's option (`<locator>@<r>`), so a level already ingested is `SKIPPED` as usual. That is how a table level joins geo levels uploaded before: the same file again with the same `geo` and `table=true` skips each geo level (its id keeps only the bands it applies) and runs the table level, whose commit places it by their events, so the graph is that of one upload of every level apart from batch ids and times (`test_the_geo_levels_first_then_the_table_is_the_upload_of_all_levels`); after the table level alone was deleted, the same upload brings it back, its themes then learned in another order of batches ([5.4](05_latent_anchors.md#54-assignment-ema-and-orphans)). The table level leaves the columns the locator finds the points in out of the table (`locator` on its batch record, `load_dataset(locator=)`, with a warning): coordinates are where an event happened, not a quantity to explain, and mined as metrics they become every pattern's target (the district condition restates `lon`). Its id therefore mixes in the left-out columns and is not a plain upload's of the same file. With `table=true` the levels share `bins` and `categories` (`strict=False` on the batch record; geo levels alone apply them strictly, as one upload does): a geo level skips the file's own columns, which the cells do not keep, and the table level skips any column it lacks, each with a warning, so `bins=median_income_median:4,median_income:4` bands the cells' median on the geo levels and the raw column on the table level; a name in neither the file nor the cells (a typo) still fails the geo levels with `invalid_options`. Every level's batch record carries `upload_id` (`up-` + 12 hex of the file's sha256, options left out: it names the file, not one upload, so two uploads of the same bytes share it, and its listing and its deletion take both) and `level` (the resolution, or `table`). The snapshot gives each level's Dataset node `upload_levels`, which the scale label reads ([7.4](07_question_answering.md#74-the-evidence-object)): the `level` of every batch record with its `upload_id`, of any status, so a failed level counts, a later upload of the same file adds its levels and a level deleted alone drops out; `resolve_levels` (`core/engine.py`) refuses with `invalid_options` a resolution listed twice or left empty (`@8,,7`) and a coarser resolution that is not one of `GEO_REGION_LEVELS`, before the file is kept. The table level has no cells of its own: its patterns are placed in the regions by their events, through the finest geo level of the upload ([6.1](06_graph_and_storage.md#61-the-structural-plane)), and are never CO_LOCATED; the anchors relate it to the geo levels. `GET /api/batches?upload_id=` lists the levels, `DELETE /api/uploads/{upload_id}` removes them all ([6.8](06_graph_and_storage.md#68-deleting-a-dataset)).

**`@auto`.** `geo=<locator>@auto` on an upload reads the levels from the points (`select_levels`, `subgroup_miner/spatial.py`; `auto_levels` reads the stored file): each point's cell at every resolution from 10 down to 3 (`GEO_AUTO_RESOLUTIONS`), and per resolution the cells, the dense ones — with at least `MIN_CELL_POINTS` points, the cells that carry medians and shares ([the cell table](#29-spatial-datasets-the-geo-option)) — (`dense_cells`), the share of the points lying in them (`dense_points`) and the median points per cell. The finest level is the finest resolution with at least `MIN_ROWS` dense cells (rows with values for the miner), `dense_points ≥ GEO_DENSE_POINTS_MIN` (0.5: most of the data described by its cells' values) and at most `GEO_AUTO_MAX_CELLS` (5,000) cap cells (when every such resolution has more, the coarsest of them). A resolution within `GEO_REGION_LEVELS` counts the cells of its region level, the finest listed level not finer than it: a pattern is IN_REGION at every listed level not finer than its own ([6.1](06_graph_and_storage.md#61-the-structural-plane)), so the cap bounds the regions one pattern can reach at the finest of them, and a listed level counts its own cells, 6 and 4 those of 5 and 3. A resolution finer than every listed level (8 to 10 under the default) or coarser than all of them counts its own cells; the coarser levels are the `GEO_REGION_LEVELS` below it that keep `GEO_AUTO_MIN_CELLS` (500) cells, `GEO_LEVELS_MAX` (3) levels in all. The two bounds were calibrated on a real event export of about 320,000 points. At 8 (35,966 cells, 0.31 of them dense) and 7 (13,403) its findings swept the map, up to 62 % and 56 % of the cells, and lay in 87,050 and 45,616 regions (IN_REGION edges); at 6 (4,211 cells; 1,116 at 5) none covered more than a quarter (4,042 edges), and mining took 46 s. At 4 (275 cells) and 3 (70) the miner's least subgroup (`max(5 · metrics, 0.5 % of the rows)`, 100–120 cells for its 20–24 metrics) left nothing to find, while 5 (1,116) found 9 findings; that export now gets 6 and 5. The export places the bound between 1,116 and 13,403 cap cells; 5,000 itself is not measured. Its own cells at 6 would cap the area a dataset covers instead of its regions: the synthetic deliveries of `scripts/perf_benchmark.py`, spread over the whole of California, have about 24,000 cells at 6 with 300,000 points and with 1,000,000 alike, 3,537 and 3,547 at 5, and get 6 and 5. A finest level that finds nothing (an `EMPTY_LEVEL` code, such as `no_candidates` or `no_viable_insights`) while finer ones were left out by the cap alone names the nearest of them in its error message (`try <locator>@<r>`), which the console shows. The upload then proceeds as `@<chosen>` (each level's dataset id is that of the explicit option), an explicit `@7,5` overrides, and every level's `profile.geo.levels` keeps `{chosen, capped, candidates: {res: {cells, dense_cells, dense_points, median_points, cap_cells}}, reasons: {res: why}}`, `capped` the resolutions the cap alone left out, finest first. Each resolution indexes the points itself, as `build_cells` does: H3 children do not tile their parent, so counting the parents of finer cells would differ from the level's cell table by a few cells, enough to choose a level that then fails `MIN_ROWS`. No resolution passing the cell and density rules refuses the upload with `invalid_options` naming each resolution's reason, and the file is not kept; points with no valid location refuse it too. The candidates stop at 3, so the region level 1 is never an `@auto` level. `candidates` and `reasons` are keyed by the resolution as text, as JSON stores them. The two density rules answer two questions. The share is taken of the points, not of the cells: a sparse file over a wide territory has most of its cells nearly empty at every fine level, and a share of cells would pass only a level as coarse as the territory, while a share of the points follows where the data lies. The count of dense cells keeps a file whose points pile up on a few spots off the level where only those spots are dense: 5,000 events on 10 depots and 2,000 scattered over about 50 km × 50 km have 0.71 of their points in 10 or 11 dense cells at 10, 9 and 8, and get 7 (197 dense cells; the case of `tests/test_auto_levels.py`). Measured with the bundled model (`scripts/perf_benchmark.py`): the script's synthetic deliveries with 30,000 points over California have 0.08, 0.12 and 0.22 of their cells dense at 7 to 5, and 0.32, 0.66 and 0.80 of their points in them; they get 6 and 5 (8,894 cells at 6, 3,236 at 5), with 13 and 7 findings, where 4 alone, outside `GEO_REGION_LEVELS`, finds 4. The shipped California table gets 6 and 5 (2,530 cells at 6, 0.87 of the points in 676 dense cells; 12 and 10 findings; 5 alone finds 10), its 7 (0.67) over the cap; the synthetic deliveries with 300,000 and 1,000,000 points get 6 and 5. A small dense file keeps its fine level and no finer: 5,000 points in a box of about 10 km get 9 (0.71 in dense cells), not 10 (3,554 cells under the cap, 0.007 in dense cells). 2,000 uniform points over 1° × 0.83° (about 111 km × 74 km) get 6, 50,000 get 7 (8 is dense enough but has 10,391 cells).

**Column roles follow the dtypes only** (no column name is interpreted):

| Source column | Cell column(s) | Kind |
|---|---|---|
| (every point) | `points` — the number of points in the cell | counter, every cell |
| datetime (or text that parses as dates, ≥ 8 characters) | `<col>_active_days` (distinct days); `<col>_late_share` (share of points after the midpoint of the whole period) | counter; intensive |
| numeric | `<col>_median` | intensive |
| categorical, 2–`GEO_MODE_MAX_LEVELS` (40) levels, *place-like* (mean top-level share over dense cells ≥ 0.9) or with more than `GEO_SHARE_MAX_LEVELS` (8) levels | `<col>_mode` — the cell's most frequent level | dimension |
| categorical, mixed within cells, ≤ `GEO_SHARE_MAX_LEVELS` levels | `share_<col>_<level>` per level (a binary column: its rarer level) present strictly between 0 and 1 in at least 10 % of dense cells | intensive |
| more levels, or a single one (identifiers, free text) | — (listed in a warning) | dropped |

A mode column nested in a share column (one column's level fixes the other's for ≥ 98 % of the rows, either direction) is dropped: its mode would restate those shares. **Intensive** columns are NaN in cells with fewer than `MIN_CELL_POINTS` (5) points — medians and shares of one to four points are noise — while counters are kept for every cell, so quiet cells stay part of the comparison. **The baseline of every shift is the set of cells holding at least one point** (the profile's `geo.base`).

**Neighbourhood conditions** are computed on all cells before any NaN rule and become text dimensions (the miner is unchanged):

| Column | Definition |
|---|---|
| `neighbours_<counter>_band` | the mean of the counter over the cell's ring-1 neighbours (`h3.grid_ring`, the cell itself excluded; a neighbour without points counts as 0), cut into quartile bands `q1…q4` by `apply_bins` |
| `lisa_points` | local Moran's I of `log1p(points)` with row-standardised ring-1 weights over the occupied cells; each cell's I is scored against its conditional-randomisation null — the cell fixed, its neighbours' values drawn from the other cells (Anselin 1995) — with that null's exact mean and variance (Sokal, Oden & Thomson 1998) under a normal approximation, so there are no permutations and the p-values have no floor on a large map (a permutation null of P draws cannot go below 1/(P+1), which a false-discovery cut over thousands of cells never passes); the p-values of the cells that have neighbours are cut at false-discovery rate 0.05 (Benjamini–Hochberg: one test per cell is a family, and uncorrected per-cell p-values would label hundreds of cells of a large map under the null); a survivor is `hot spot` (high, high neighbours), `cold spot`, `high outlier` or `low outlier`; every other cell `no cluster` |

These conditions are always among the searched dimensions: they are prepended to step 2's choice (so a geo dataset searches up to six dimensions plus its neighbourhood conditions; `COMPUTE_BUDGET` still bounds the conjunctions). A condition never explains what it is computed from (`SpatialContext.derived_from`): a neighbourhood condition never explains a counter, and a mode condition never explains the shares of a column it is nested with (≥ 90 % of the rows). How the rule is applied: *Tautologies never reach the rank*, below.

**Two neighbourhoods, on purpose.** The band counts an absent ring neighbour as 0 and averages over the whole ring (`spatial_lag` with `ring`): a cell next to empty space has quiet surroundings, and that is what the band measures. Moran's I and LISA average over the occupied neighbours only (`ring` = None): autocorrelation is a property of the values that exist. The two read different questions and are not unified.

**Tautologies never reach the rank.** A neighbourhood condition restates the counters it was built from (`SpatialContext.derived_from`: the bands and `lisa_points` → every counter; a mode nested in a share column → those shares), so pass 1 scores no such (dimension, metric) pair, neither as a shift nor inside the correlation change (`step4_evaluate_micro_slices(forbidden=)`): a hot-spot cohort is ranked by what else is special about it, not by the `points` it is busy by construction, and the validation budget is spent on shifts that are allowed to exist. The closure of [2.3](#23-deduplication-before-validation) can add such a condition to a cohort found through another one, so the rule is applied once more at closure: the metrics the closed conditions are computed from are the cohort's `restated` set, their shifts leave `top_shifts` there (the shift score is re-summed and the correlation change re-scored over the other metrics), the validation never reports them as hidden shifts, and the covariance pair is searched among the other metrics. A cohort left with no shift stands on its covariance pair alone: with one it can become a covariance insight, without one it is rejected as `tautological` before the rank and spends no validation slot. (A plain-table cohort in which no metric has a median — every value missing — is rejected at the same point as `no_shift`.)

**Spatial autocorrelation.** Neighbouring cells are not independent, so the median test of [2.4](#24-what-the-adapter-adds) runs on an effective sample size: `n_eff = n · (1 − ρ) / (1 + ρ)` — the one-parameter approximation of Clifford, Richardson & Hémon (1989) — with `ρ = max(0, I_S)`, `I_S` the Moran's I of the primary metric over the **subgroup's own cells and the ring-1 links that stay inside it** (`subgroup_moran`): a solid block of similar cells is discounted, thirty scattered cells have no inside links and are not; the global I of each metric stays on the profile as a description of the map. `se = 1.2533 · 1.4826 · MAD / √n_eff`. The same dependence reaches `stability`: for spatial data the step-4b bootstrap resamples **blocks** — a cell's parent cell one resolution coarser (`SpatialContext.blocks`), drawn with replacement, each drawn block contributing all its cells — instead of cells, so neighbouring cells stay together as they would in an independent sample; a small extent spans few parents, and over k parents the bootstrap has at most k^k distinct resamples, so its `stability` is coarse. A draw whose blocks hold no value of a shifted metric (sparse cells carry no intensive metric) scores nothing and is skipped; a cohort with no scoring draw gets the full instability penalty. Each insight records `provenance.spatial = {resolution, cells, moran_i (the subgroup's), n_eff, p_adjusted_iid}` (the Bonferroni-adjusted p without the correction), and the profile's `geo.sac = {validated, significant_iid, significant_corrected, admitted}` counts the validated candidates with `p_adjusted ≤ MAX_P_ADJUSTED` without and with the correction.

After admission the graph service stores the cells, the point → cell map, the points and the neighbour graph as `datasets/<ds>/geo.npz`, and writes the map's GeoJSON from the cell table (`cells.geojson`); every commit derives the spatial plane from these files — regions, CO_LOCATED links, each pattern's compactness ([6.1](06_graph_and_storage.md#61-the-structural-plane)); the profile also carries `geo.glossary`, the plain-language meaning of every derived column the answers use ([7.4](07_question_answering.md#74-the-evidence-object)) ([6.3](06_graph_and_storage.md#63-the-workspace-on-disk)).

> **Measured** on the map demo (California housing, 20,640 block groups, `geo=auto@5`, `bins=median_income_median:4`): 884 cells (540 below `MIN_CELL_POINTS`), global Moran's I of the metrics 0.33–0.72; 53 distinct cohorts, 12 of them dropped before the rank as tautological, 39 validated, 18 insights admitted (one a correlation change, three on a `hot spot` scope); of the 39 validated 26 are significant without and 17 with the subgroup-level `n_eff` correction; the subgroups' own Moran's I runs from below 0 (scattered cells: no discount) to 0.71 (a solid inland block of 616 cells, `n_eff` 33).

**Why the H3 hierarchy groups places, not community detection.** The regions are H3 cells at `GEO_REGION_LEVELS`, fixed by the grid: a region has the same id (`R:<res>:<h3>`) for every dataset, batch and commit, and a new dataset adds members to it without moving its border. A cell joins the region holding its centre by one rule on every platform, a centre on a border to its H3 parent ([6.1](06_graph_and_storage.md#61-the-structural-plane)). Communities found on the graph (Leiden, as GraphRAG builds its summaries) would be recomputed with every commit. Their ids and borders would change with the data, and two sources could not be compared at one place. That comparison is what credibility by place reads ([13.3](13_trust.md#133-credibility-levels)). **Time is not an axis of the spatial plane.** Datasets carry no time slice, and a region holds the findings of every period uploaded. A time axis is the next product iteration, not this one. Nothing in `SpatialProvenance` or `derive_spatial` assumes that all datasets describe one moment.
